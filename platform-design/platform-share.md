# 01 背景与目标

## 1.1 建设背景

**行业痛点：软件造价评估"难、慢、散、糊"**

- **难**——功能点计数、人月费率、调整系数，专业门槛高，认证造价师稀缺，评估能力集中在少数专家身上；
- **慢**——单个项目的造价评估以周计，评估节奏直接制约立项与预算下达节奏；
- **散**——需求、估算、预算、测试、验收各环节工具烟囱式割裂，同一份数据反复录入、口径不一；
- **糊**——最终报价说不清来源：对应哪些需求、哪些功能点、哪条用例验证？事后翻文档拼不出来，审计取证难。

**现实挑战：专家经验在个人、不在组织**

历史项目的功能点数、实际工期、实际成本散落在 Excel 和"老法师"的脑子里；人员一变动，知识即流失。评估能力依赖人力堆叠，无法随项目数量扩展——这对任何一家把软件研发当核心投入的机构都是结构性风险。

**技术浪潮：Agent 工程范式走向成熟**

大模型 + 智能体框架的能力栈已经闭环：工具调用、RAG 检索、长期记忆、人机确认、沙箱执行。让"懂造价流程的智能体流水线"从概念变为可工程化落地的产品，条件已经具备；国产模型（本平台接智谱 GLM，Anthropic 兼容端点）达到生产可用水平，内网部署无障碍。

**标准东风：造价本来就不是玄学**

GB/T 36964《软件研发成本度量规范》、NESMA 功能点计数法、行业价格基准——评估有据可依、有表可查。**标准化的流程恰恰是智能体最擅长的"照章办事"**：方法论越成熟，越适合数字化为提示词契约与结构化数据。反过来，平台也把标准固化下来，让每个项目天然按同一把尺子度量。

## 1.2 建设目标

立足标准东风与技术浪潮，围绕**需求生成、原型设计、工时预算、测试用例、测试执行、验收审计**六大环节，建设一个"**智能体干活、人把闸门、全程留痕**"的软件全生命周期管控平台：每个阶段由专属智能体辅助产出，每个产物必须经人工审批才能进入下一阶段，退回可修订重开、意见随轮次留痕；全程数据从需求到报价可追溯，项目经验沉淀为组织资产。最终让造价评估从"依赖个别专家"变成"依赖平台能力"，达成**提效、控险、沉淀资产**的三重目标。

# 02 体系架构

## 2.1 业务架构：六阶段流水线 × 两级状态机 × 两层 HITL

```
┌────────┐   ┌────────┐   ┌──────────┐   ┌────────┐   ┌────────┐   ┌─────────┐
│①需求生成│──▶│②原型设计│──▶│③工时预算  │──▶│④测试用例│──▶│⑤测试    │──▶│⑥验收审计 │
│ 智能体  │审 │ 智能体  │审 │ 罗盘智能体│审 │ 智能体  │审 │ 智能体  │审 │ 智能体   │
└────────┘批 └────────┘批 └──────────┘批 └────────┘批 └────────┘批 └─────────┘
   PRD         原型HTML      功能点清单/    用例文档      测试报告      结算/审计
                            预算表                     (功能+单元)     汇总报告
              ▲                                                       ▲
              └──── 人工审批不通过则退回当前阶段修订（round+1，可多轮）──────┘
```

三个关键设计贯穿这张图：

- **两级状态机**：项目级（DRAFT → ACTIVE → ACCEPTED → ARCHIVED）管项目一生；阶段运行级（in_progress → under_review → approved / returned）管每一次阶段协作。三重守卫保证流程纪律：阶段必须按序串行、同阶段不允许并存活跃 run、已 approved 不可重开——非法转移直接 409/400，而不是靠人自觉。
- **两层 HITL，互不替代**：**微观**是对话内的工具确认——智能体要调敏感工具时运行时挂起，人在工作台逐个"允许/拒绝"（可一键全部允许，切 `accept_edits` 权限模式）；**宏观**是阶段产物的审批裁决——对话满意后提交送审，审批人通过则自动推进，退回则必须填意见、同阶段重开新轮次，退回意见随 kickoff 注入新会话。
- **六智能体全局共享**：六个阶段智能体定义在运行时、全局一套（挂在内部主体 `sys:runtime` 名下），项目创建零智能体开销；"定义共享、状态随会话"——同一智能体开 N 个会话互不污染。智能体由脚本幂等播种，每个的提示词就是一份岗位说明书。

业务硬性要求（每一条都对应架构决策）：多租户（组间隔离、知识库按组授权）、长周期项目（数月跨度、项目→阶段→会话层级）、人工审批全留痕（银行审计要求）、双形态部署（公有云 K8s + 内网全离线）、会话隔离与并发互斥、跨阶段交接与跨项目沉淀。

## 2.2 总体架构：控制面 / 执行面分离的三层

```
┌─────────────────────────────────────────────────────────────┐
│ 前端 SPA（React 19 + Vite，一套代码、两个视图）                  │
│  视图A·项目生命周期（看板/详情/甘特/审批/版本链/追溯矩阵）          │
│  视图B·Agent 工作台（左:项目上下文 中:对话 右:产物预览）           │
└──────────────────────┬──────────────────────────────────────┘
                 HTTPS/JWT│  前端只对接编排层（BFF 模式）
┌──────────────────────▼──────────────────────────────────────┐
│ 业务编排层 L1（自研 FastAPI，platform/backend）——平台的"控制面"   │
│  用户/组/RBAC · 项目管理 · 阶段状态机 · 审批任务 · 产物版本链       │
│  知识库授权 · 项目档案(跨阶段记忆) · 价格基准 MCP · 管理视图        │
│  业务库: PostgreSQL（platform 库）     依赖仅 9 个包、不 import   │
└──────┬─────────────────────────────────────────────────────┘
       │ HTTP（X-User-ID: sys:runtime）——唯一的出网口是防腐层
┌──────▼─────────────────────────────────────────────────────┐
│ 智能体运行时层（AgentScope，examples/platform_agent_service）    │
│  6×阶段智能体 · 会话/上下文压缩 · 工具/技能/MCP · RAG 检索         │
│  项目工作区(产物落盘) · 长期记忆中间件 · SSE 事件流                │
│  会话/消息/KB 元数据: PostgreSQL（agentscope 库）                │
│  消息总线/分布式锁: Redis   向量检索: 内嵌 Qdrant 本地落盘         │
└─────────────────────────────────────────────────────────────┘
```

**三条核心原则**，后面所有设计都从这三条推导：

1. **控制面与执行面分离**。业务流程（谁审批、走到哪步、产物哪个版本有效）是普通工程问题，用普通工程手段解决（数据库 + 状态机，收敛在 `flow.py` 约 200 行，不引 BPMN 引擎）；智能体只负责"阶段内的智力劳动"。不要把业务流程塞进 Agent 的自治协作里。
2. **AgentScope 不直接面向最终用户**。所有前端流量过编排层（BFF 模式）：鉴权、授权、审计、租户隔离收敛一处；运行时退居内网，是编排层的"智能体引擎"。
3. **平台用户体系与运行时主体解耦**。运行时只见 `sys:runtime` 一个内部主体，平台的用户/组织/权限体系完全自己持有，两条用户体系永不纠缠。

防腐层（`runtime_client.py`）是 L1 唯一访问运行时的模块，刻意收窄为 8 个类型化操作，换来三个红利：① 运行时连不上统一 503、自身出错统一 502，前端拿到干净错误码而非内部堆栈；② 运行时凭证接口本会返回明文 api_key，防腐层把 key 字段剥掉、只放行 id/名称/类型——**key 在物理上不可能出现在 L1 的日志或响应里**；③ 上游框架升级改了 HTTP 接口，L1 只有这一个文件要跟着改。

## 2.3 技术架构：组装而不改造

平台对 AgentScope（开源智能体框架）的用法是**"独立目录 + 组装参数"**，一行框架源码不改，上游有值得跟进的改动时手工 cherry-pick。运行时组装三件套，把上游"单机演示形态"组装成"多实例生产形态"：

| # | 组件 | 上游默认 | 平台组装 | 得到什么 |
|---|---|---|---|---|
| 1 | 存储 | `RedisStorage`（内存态） | `AsyncSQLAlchemyStorage` → PG 库 `agentscope` | 持久落盘、可审计、多实例共享 |
| 2 | 消息总线 | `InMemoryMessageBus`（单进程） | `RedisMessageBus` | 多副本部署；分布式会话锁（两级：同进程双投递 409，跨副本投递排队串行）+ SSE 事件回放 |
| 3 | 下载签名密钥 | 每次启动随机 | 固定值（环境变量） | 签名下载链接跨重启、跨实例验签一致 |

知识库体系按用途分五类，权限全部在编排层执行：

| 类型 | 内容 | 形态 | 主要消费阶段 |
|---|---|---|---|
| 行业规范库 | 监管文件、软件工程规范、造价标准 | 文档 RAG | ①④⑥ |
| 价格基准库 | 功能点单价、地区系数、人月费率 | **结构化表 + 文档双轨** | ③ |
| 案例库 | 历史项目档案（功能点数/工期/成本） | 结构化 + RAG | ③⑥ |
| 模板库 | PRD / 测试用例 / 审计报告模板 | 文档 | ①②④⑥ |
| 沉淀库 | 项目经验、系数修正、常见问题 | 文档 RAG | 全阶段 |

- **价格基准走双轨**：核心数值（单价/系数）放结构化表 `price_items`，预算智能体通过 MCP 工具精确查询（`query_price_baseline`，由 L1 挂载、运行时以 streamable-http 消费），说明性文档才走 RAG。提示词明确"费率必须查工具、不得凭记忆报价"——**造价场景的数字必须可审计，不能让模型"检索着算"**。
- **授权检索先过滤后检索**（authorization-aware RAG）：用户可见 KB = 组授权 ∪ 用户例外，再与项目阶段绑定取交集；权限不通过的知识库根本不进入检索候选，而不是检索完再过滤。
- **向量索引不引独立服务**：进程内嵌 Qdrant 本地落盘（只是 pip 依赖），每 KB 一个独立集合、天然按库隔离，索引随运行时重启保留；多实例部署时再评估共享实例或换向量后端。
- **记忆三层**：会话内靠上下文压缩；跨阶段靠项目档案（上游产物与退回意见随 kickoff 注入）；跨项目靠沉淀库（项目结束沉淀入库，M4 已走通审批闭环）。工作区里智能体自己写的长期记忆（问卷澄清记录、FR 标注来源）与权威归档（`artifact_versions` 不可变版本链）分层——工作区丢了可从归档恢复，归档是业务的事实源。
- **模型策略**：平台默认模型 + 按智能体蓝图可覆盖（接智谱 GLM），用户全程无感知，前端零配置。

## 2.4 安全架构：四层防护

| 层 | 机制 |
|---|---|
| **用户层** | JWT 登录（scrypt 口令哈希）+ RBAC（owner / approver / member）+ 资源 ACL；自助注册自动入 `default` 组，管理员调整部门归属；预留 LDAP/OA 对接 |
| **接入层** | BFF 单一入口，前端永不出网；防腐层收窄为 8 个类型化操作；凭证安全投影——api_key 只活在运行时，L1 侧物理上不可见 |
| **应用层** | 工作区隔离：文档类阶段 `proj-{id}` 项目共享、测试阶段 `test-run-{run_id}` 每次运行独立沙箱；HITL 工具确认 + 权限模式（ASK → 可切 accept_edits）；知识库先过滤后检索防泄漏 |
| **支撑层** | 运行时主体收敛 `sys:runtime`（外部用户名永不下沉到运行时）；分布式会话锁（两级互斥：同进程双投递 409，跨副本投递排队串行——双副本实测）；工作区文件下载走 HMAC 签名链接（默认 60 秒有效）；状态机三重守卫；`approval_tasks` 审批留痕表 + 产物不可变版本链 |

# 03 主要创新点

## 3.1 业务创新点

**① 全生命周期闭环，而非单点提效**

同一项目从需求到验收一条流水线：上游产物自动注入下游 kickoff，退回意见随重开轮次注入。对比"每个环节买一个 AI 工具、人肉在环节之间搬运数据"，平台让数据在系统内流转——需求编号 FR-xx 贯穿到功能点 FP-xx、测试用例 TC-xx、报价行，一次录入全程引用。

**② HITL 人机协同：智能体干活、人把闸门**

微观（对话内工具确认）+ 宏观（阶段产物审批）两层介入，各有分工、互不替代。智能体的产出永远是"待审稿"——没有人点头，流程不流转。这回应了金融场景的核心关切：**AI 可以承担专业劳动，但责任边界必须清晰在人**。

**③ 文档先行、全程可审计**

项目 → 阶段 → 轮次 → 产物四级留痕，产物是不可变版本链，审批人/意见/时间全记录。架构设计先于代码（`architecture.md` 是开发的唯一依据），每个决策有出处。造价数字全部可回溯：需求 → 功能点 → 用例 → 报价一条链（见 3.2-②）。

**④ 知识沉淀闭环：项目经验回流组织资产**

阶段产出沉淀项目记忆，项目结束走审批入沉淀库与案例库；下一个项目估算时，历史项目的功能点数、实际工期、实际成本成为参照。把"老法师脑子里的经验"变成"平台上可检索的资产"，人员变动不再等于知识流失。

**⑤ 造价方法论数字化：agents classify, platform prices**

NESMA 估算功能点法落地为提示词契约 + 结构化数据：智能体只负责把需求分类成 ILF/EIF/EI/EO/EQ 五类功能点，加权计数（ILF=7 / EIF=5 / EI=4 / EO=5 / EQ=4）由平台统一给定，费率从结构化价格基准表精确查询。**模型负责理解语义，数字的权威在平台**——这是把大模型用在它擅长的地方、把确定性留给人可以审计的地方。

## 3.2 技术创新

### 技术创新 1：状态机编排 + kickoff 交接协议，替代 BPMN 引擎与 Agent 自治协作

长周期流程（数月、数百次人机交互）的编排，业内常见两条路：BPMN 工作流引擎（Activiti/Camunda），或 Agent 自治协作（智能体互相商量着推进）。我们两条都不走：**两级状态机收敛在 `flow.py` 约 200 行**，配合 `stage_runs`（轮次）/ `approval_tasks`（审批留痕）/ `artifact_versions`（版本链）三张表。

- 为什么不放 Agent 自治协作里：流程横跨数月，状态必须落在持久化数据库而非会话上下文；审批人/意见/版本锁定是业务数据不是对话内容；Agent 无状态可重跑，流程状态永不依赖某个会话是否存活。
- **kickoff 交接协议**：每个新会话的启动消息由 L1 组装——注入上游已批准产物 + 本阶段任务说明 + 退回意见（重开轮次时）。跨阶段交接不靠智能体"记得"，靠协议保证。

### 技术创新 2：追溯矩阵——需求 → 功能点 → 测试用例 → 报价的结构化侧表

造价交付要回答"这笔钱对应哪些需求、哪些功能点、哪条用例验证"，靠事后解析产物文档拼不出来（文档格式随用户要求变化，解析链脆弱）。平台的解法是**在文档产物旁边铺一条机器可读的侧表轨道**：

- **写入**：四个文档阶段智能体在人读文档之外，往工作区根目录写 `req-table.json` / `fp-table.json` / `tc-table.json` / `budget-table.json`——提示词契约的一部分，字段固定、逐轮可校验；
- **入库**：审批通过的钩子从工作区收割侧表入四张追溯表（键 = stage_run_id）；缺文件/坏 JSON 只记 warning，**永不阻断审批**；只有已批准数据入库，读侧取每阶段最新已批准轮次；
- **读侧**：项目详情页"功能点与追溯"卡渲染贯通矩阵——UFP=Σ权重、工时合计、每切片来自哪个 run。

配合"agents classify, platform prices"的定价纪律（3.1-⑤），报价表里每个数字都能点到源头。

### 技术创新 3：授权感知检索 + 价格基准双轨

- **先过滤、后检索**：权限判定在编排层完成，不通过的知识库不进入检索候选——防泄漏（不会把无权内容检索出来再过滤）也省算力；
- **价格基准双轨**：数值进结构化表、由 MCP 工具精确查询（走查中预算智能体实调 7 次，含"北京无生产率基准 → 自动回退全国基准"的空结果恢复）；说明性文档才进 RAG。让"检索增强"服务理解、让"工具查询"服务计算。

### 技术创新 4：工作区与沙箱隔离

- **共享工作区目录钉死**：上游工作区管理器的目录按智能体解析，跨阶段共享的项目工作区（`proj-{id}`）在缓存逐出后会静默断裂。平台以约 30 行的子类把共享 id 钉死目录——同一项目六个阶段的智能体真正共享同一目录，项目记忆与中间产物不断链；未命中约定的 id 保持上游行为不变；
- **阶段运行级沙箱**：测试阶段每次运行拿独立工作区（`test-run-{run_id}`），与文档阶段的共享工作区物理分开；M5 计划升级为每 stage_run 一个专用 Docker 沙箱——"智能体放手操作、不出乱子"。

### 技术创新 5：不改框架的组装式集成

对开源框架（AgentScope）的态度是**组装而不改造**：运行时组装三件套 + 防腐层 + 30 行子类，实现平台的全部增量能力；L1 编排层依赖仅 9 个包、不 import agentscope。收益：上游升级零冲突（cherry-pick 纪律）、框架的安全与并发能力（分布式会话锁、SSE 回放、权限暂停）原样继承、代码长期可维护。这一实践已单独成文（`agentscope-share.md`）。

## 4.2 端到端验证：13 分钟全六阶段走查

`scripts/walkthrough.py` 以假项目 #19 完成全流程自动化走查，一次运行验证三件事：

- **六阶段闭环**：需求 → 原型 → 工时预算 → 测试用例 → 测试 → 验收审计全部走通，**含一次退回重做**（退回意见注入重开轮次，round+1）；
- **工具链真实调用**：预算智能体实调 price-baseline MCP **7 次**查准费率，其中"北京无生产率基准"的空结果被提示词约束引导自动回退全国基准——工具异常路径也在验证范围内；
- **隔离真实生效**：文档阶段共享 `proj-{id}` 工作区、测试阶段切 `test-run-{run_id}`，同一项目两类工作区物理分开。

配套验收：M3 权限与价格基准十个用例全过（跨组检索 403 / 非管理员导入 403 / MCP 精确返回导入值 / 无向量化凭证创建 KB 优雅 503 零落库）；M4 沉淀闭环以 2353 字真实草稿走完审批；**M5 `verify_m5.py` 11 项全过（97 秒）**——脚本自动拉起 8001 副本（同 PG+Redis）：六智能体双副本可见、A 建会话 B 发消息、A 经共享 Redis 锁观察到 B 的运行、跨副本 SSE 事件流、进程内双投递 409、跨副本排队串行后两条回答落库、L1 故障转移（死地址→副本）、md→docx/xlsx 导出、`--no-index` 离线 venv 安装。

## 4.3 预期效益

> 以下为设计目标，量化数据待真实项目运行后由统计看板沉淀（刻意不编数字）：

- **提效**：评估主链（需求结构化 → 功能点计数 → 预算表）从专家人天级压缩到小时级——走查已证明全流程 13 分钟可跑通，真实项目按审批节奏以天计；
- **控险**：报价数字全部可追溯（NESMA 权重平台统一、费率查结构化表），审计取证从"翻文档"变成"查追溯矩阵"；AI 产出全部过人工闸门，责任边界清晰；
- **沉淀**：每个项目自动形成案例档案（功能点数/工期/成本），新项目估算自动参照同类历史——评估准确率随使用量提升，而非随人员经验波动。
