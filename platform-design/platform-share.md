# 01 背景与目标

## 1.1 建设背景

**行业痛点：软件造价评估"难、慢、散、糊"**

- **难**——功能点计数、人月费率、调整系数，专业门槛高，认证造价师稀缺，评估能力集中在少数专家身上；
- **慢**——单个项目的造价评估以周计，评估节奏直接制约立项与预算下达节奏；
- **散**——需求、估算、预算、测试、验收各环节工具烟囱式割裂，同一份数据反复录入、口径不一；
- **糊**——最终报价说不清来源：对应哪些需求、哪些功能点、哪条用例验证？事后翻文档拼不出来，审计取证难。

**现实挑战：专家经验在个人、不在组织**

历史项目的功能点数、实际工期、实际成本散落在 Excel 和"老法师"的脑子里；人员一变动，知识即流失。评估能力依赖人力堆叠，无法随项目数量扩展——这对任何一家把软件研发当核心投入的机构都是结构性风险。

**技术浪潮：Agent 工程范式走向成熟**

大模型 + 智能体框架的能力栈已经闭环：工具调用、RAG 检索、长期记忆、人机确认、沙箱执行。让"懂造价流程的智能体流水线"从概念变为可工程化落地的产品，条件已经具备；国产模型（本平台接智谱 GLM，Anthropic 兼容端点）达到生产可用水平，内网部署无障碍。

**标准东风：造价本来就不是玄学**

GB/T 36964《软件研发成本度量规范》、NESMA 功能点计数法、行业价格基准——评估有据可依、有表可查。**标准化的流程恰恰是智能体最擅长的"照章办事"**：方法论越成熟，越适合数字化为提示词契约与结构化数据。反过来，平台也把标准固化下来，让每个项目天然按同一把尺子度量。

## 1.2 建设目标

立足标准东风与技术浪潮，围绕**需求生成、原型设计、工时预算、测试用例、测试执行、验收审计**六大环节，建设一个"**智能体干活、人把闸门、全程留痕**"的软件全生命周期管控平台：每个阶段由专属智能体辅助产出，每个产物必须经人工审批才能进入下一阶段，退回可修订重开、意见随轮次留痕；全程数据从需求到报价可追溯，项目经验沉淀为组织资产。最终让造价评估从"依赖个别专家"变成"依赖平台能力"，达成**提效、控险、沉淀资产**的三重目标。

**业务硬性要求**（每一条都对应一个架构决策）：

| 要求 | 含义 |
|---|---|
| 多租户 | 用户属于组（部门），组间数据隔离；知识库按组授权 |
| 长周期项目 | 项目持续数月，需要项目 → 阶段 → 会话的层级 |
| 人工审批 | 每阶段闸门，不同阶段可由不同负责人审批，全部留痕（银行审计要求） |
| 双形态部署 | 云端多实例 + 银行内网全离线，同一套代码 |
| 会话隔离 | 用户隔离、项目隔离、会话级隔离（并发互斥） |
| 记忆与沉淀 | 阶段内多轮交互，跨阶段有交接，跨项目有沉淀 |

# 02 体系架构

## 2.1 业务架构：六阶段流水线 × 两级状态机 × 两层 HITL

```
┌────────┐   ┌────────┐   ┌──────────┐   ┌────────┐   ┌────────┐   ┌─────────┐
│①需求生成│──▶│②原型设计│──▶│③工时预算  │──▶│④测试用例│──▶│⑤测试    │──▶│⑥验收审计 │
│ 智能体  │审 │ 智能体  │审 │ 罗盘智能体│审 │ 智能体  │审 │ 智能体  │审 │ 智能体   │
└────────┘批 └────────┘批 └──────────┘批 └────────┘批 └────────┘批 └─────────┘
   PRD        原型HTML     功能点清单/    用例文档      测试报告      结算/审计
                          预算表                      (功能+单元)     汇总报告
```

每个阶段一道人工闸门；审批不通过则退回当前阶段修订（同阶段重开新轮次，可多轮）。

**两级状态机管"流程纪律"**——项目级（草稿 → 进行中 → 已验收 → 已归档）管项目一生；阶段运行级（未开始 → 人机协作中 → 待审批 → 已通过/已退回）管每一次阶段协作：

```
                ┌─────────────┐
  上一阶段通过   │   未开始     │
 ─────────────▶ │             │
                └──────┬──────┘
                       │ 开启（纯数据库操作，不依赖智能引擎）
                       ▼
                ┌─────────────┐     提交产物送审
     退回修改    │  人机协作中   │ ─────────────────┐
  ◀──────────── │             │                   ▼
  （必须附意见）  └─────────────┘           ┌──────────────┐
        │                                 │   待审批      │
        │    同阶段重开（轮次+1，            │              │
        │    退回意见注入新会话）            └──────┬───────┘
        └───────────────────────────────── 通过 │ 退回
                                            ▼
                                    ┌──────────────┐
                                    │   已通过      │──▶ 下一阶段待开启
                                    └──────────────┘
```

**三重守卫**保证流程纪律，非法状态转移直接被拒绝（409/400），而不是靠人自觉：阶段必须按序串行；同阶段不允许并存活跃运行；已通过的阶段不可重开。

**两层 HITL（人在回路），互不替代**：

- **微观——对话内工具确认**：智能体要调敏感工具时运行挂起，人在工作台逐个"允许/拒绝"（可一键全部允许）：

```
智能体要调敏感工具 → 引擎挂起运行、工具调用置"待确认"
  → 工作台弹出确认条（逐个工具名）→ 用户允许/拒绝
  → 编排层鉴权后回执 → 引擎恢复挂起的运行
```

- **宏观——阶段产物审批裁决**：对话满意后提交送审，审批人通过则推进、退回则必须填意见并重开轮次：

```
「提交产物送审」→ 产物快照定格为不可变版本 → 运行置"待审批"、生成审批任务
  （默认给项目审批人角色；成员变动时在途任务自动改道给项目负责人）
审批人在审批中心裁决
  → 通过：推进项目当前阶段，下一阶段待开启
  → 退回：必须填意见；同阶段重开新一轮次，退回意见随启动消息注入新会话
```

**六智能体全局共享**：六个阶段智能体定义在智能引擎、全局一套（挂在内部服务主体 `sys:runtime` 名下），项目创建零智能体开销；**定义共享、状态随会话**——智能体的完整上下文挂在会话而非智能体上，同一智能体开 N 个会话互不污染（机制保证，不是"一般不会串"）。智能体由脚本幂等播种，每个的提示词就是一份岗位说明书。会话粒度 = 一次阶段运行：每个运行各开新会话，退回重做从干净上下文开始、上一轮草稿留在共享工作区可供重读。

```
│   6×阶段智能体 · 会话/上下文压缩 · 工具/技能/MCP · RAG 检索            │
│   长期记忆中间件 · 工作区与沙箱 · SSE 事件流                          │
│   引擎库：PostgreSQL（会话/消息/知识库元数据）                        │
└──────┬────────────────┬───────────────────┬─────────────────────┘
       ▼                ▼                   ▼
  Redis（消息总线 /    向量索引（内嵌        模型服务（行内推理 /
  分布式锁 / SSE 回放）  向量库本地落盘）       智谱 GLM 兼容网关）
```

> 说明：网关中枢层与业务编排层在当前实现中同属一个自研后端服务（FastAPI）、同进程部署——逻辑上分层、边界清晰，将来需要时（如前置独立网关、多副本扩展）可平滑拆分。智能引擎层是独立部署的开源智能体框架服务，与编排层之间是 HTTP 边界（网络接口是最容易做版本化的耦合形式），而非库级依赖。

**三条核心原则**，后面所有设计都从这三条推导：

1. **控制面与执行面分离**。业务流程（谁审批、走到哪步、产物哪个版本有效）是普通工程问题，用普通工程手段解决（数据库 + 状态机，全部编排逻辑收敛在一个约 200 行的模块，不引 BPMN 引擎）；智能体只负责"阶段内的智力劳动"。不要把业务流程塞进 Agent 的自治协作里。
2. **智能引擎不直接面向最终用户**。所有前端流量经过网关中枢层（BFF 模式）：鉴权、授权、审计、租户隔离收敛一处；引擎退居内网，是编排层的"智能体引擎"。
3. **平台用户体系与引擎主体解耦**。引擎只见 `sys:runtime` 一个内部服务主体；平台的用户/组织/权限体系完全自己持有，两条用户体系永不纠缠。"谁能看哪个会话"由编排层判断后透传——可见性规则只有一个真相来源。

**防腐层**是网关中枢层访问智能引擎的唯一模块，刻意收窄为 8 个类型化操作，换来三个红利：

- ① 引擎连不上统一报 503、引擎自身出错统一报 502，前端拿到干净错误码而非内部堆栈；
- ② 引擎的凭证接口本会返回明文 api_key，防腐层把 key 字段剥掉、只放行 id/名称/类型——**key 在物理上不可能出现在编排层的日志或响应里**；
- ③ 开源框架升级改了 HTTP 接口，平台只有这一个文件要跟着改。

**一次阶段协作的完整时序**：

```
用户(工作台)         编排层                     智能引擎
   │ 发消息              │                        │
   ├──────────▶│ 鉴权：是项目成员？阶段进行中？       │
   │           │ 投递（agent_id, session_id, 消息）──▶ 获取分布式运行锁
   │           │◀── 已受理                          │
   │           │ 订阅事件流 ◀═══ SSE（增量消息/工具卡/确认卡）═══│
   │           │      ……智能体推理/调用工具/检索知识库……  │
   │ 「提交送审」│                        │
   ├──────────▶│ 快照产物 → 不可变版本；状态机流转、生成审批任务
   │  审批人裁决 │                        │
   ├──────────▶│ 通过 → 推进当前阶段；下一阶段开启时组装启动消息
   │           │   （项目档案 + 上游已批准产物 + 本阶段任务）→ 引擎首轮产出
```

下游智能体的首轮产出是"被流程驱动"的——用户进会话时往往已有初稿可改。

## 2.3 技术架构：组装而不改造

### 2.3.1 选型：形态匹配优先于功能数量

平台启动前对市面主流开源智能体框架做了系统评估。候选其实分**四个物种**：编排库（只提供流程编排原语，服务层全部自己写）、超级智能体应用（拿来即用的成品）、可视化低代码平台（画布拖拽，自带编排层）、插件化运行时。**选型错位比功能差距更致命**——用应用或平台做底座，最终都会与自研编排层打架：要么它反过来吞掉编排层，要么许可证条款限制多租户商用。

最终选定的开源框架同时满足四项硬指标：

- **SDK 可嵌入 + 服务层一体**：既能当库组装，也自带开箱的多租户 HTTP 服务层（会话/凭证/知识库/工作区全套 REST API + 事件流）；
- **Apache-2.0 协议**：商用最友好、无附加条款；
- **MCP（模型上下文协议）内建**：工具接入走开放标准；
- **原生多实例**：多租户、多会话、分布式部署是一等公民。

### 2.3.2 组装三件套：把"单机演示形态"组装成"多实例生产形态"

平台对开源框架的用法是**"独立目录 + 组装参数"**，一行框架源码不改；上游有值得跟进的改动时手工 cherry-pick，可上游化的补丁提回官方。运行时只动三个组装参数：

| # | 组件 | 框架默认 | 平台组装 | 得到什么 |
|---|---|---|---|---|
| 1 | 存储 | 内存态存储 | 异步 SQL 存储 → PostgreSQL | 持久落盘、可审计、多实例共享 |
| 2 | 消息总线 | 进程内总线 | Redis 消息总线 | 多副本部署；分布式会话锁 + SSE 事件回放 |
| 3 | 下载签名密钥 | 每次启动随机 | 固定值（环境变量） | 签名下载链接跨重启、跨实例验签一致 |

**诚实清单（能力对照）是工程纪律的起点**：框架已有的（多轮对话、上下文压缩、长期记忆、知识库全链路、工具/技能/MCP、沙箱工作区、多实例）直接用；框架没有的（文档导出、组级权限、跨天业务流程与审批）**全部自建且不假装有**——在设计文档里逐项列清"已有 vs 需自建"，不把不存在的能力当依赖。平台能力不靠改框架，靠"独立目录 + 组装参数 + 自研编排层与前端"。

### 2.3.3 知识库体系：五类分库，授权与计算各归其位

| 类型 | 内容 | 形态 | 主要消费阶段 |
|---|---|---|---|
| 行业规范库 | 监管文件、软件工程规范、造价标准 | 文档 RAG | ①④⑥ |
| 价格基准库 | 功能点单价、地区系数、人月费率 | **结构化表 + 文档双轨** | ③ |
| 案例库 | 历史项目档案（功能点数/工期/成本） | 结构化 + RAG | ③⑥ |
| 模板库 | PRD / 测试用例 / 审计报告模板 | 文档 | ①②④⑥ |
| 沉淀库 | 项目经验、系数修正、常见问题 | 文档 RAG | 全阶段 |

- **价格基准走双轨**：核心数值（单价/系数）放结构化表，预算智能体通过 MCP 工具**精确查询**（工具由编排层挂载、引擎以标准协议消费），说明性文档才走 RAG。提示词明确"费率必须查工具、不得凭记忆报价"——**造价场景的数字必须可审计，不能让模型"检索着算"**。
- **授权检索先过滤后检索**（authorization-aware RAG）：用户可见知识库 = 组授权 ∪ 用户例外，再与项目阶段绑定取交集；**权限不通过的知识库根本不进入检索候选**，而不是检索完再过滤——防泄漏也省算力。
- **向量索引不引独立服务**：进程内嵌向量库本地落盘（只是一个依赖包），每个知识库一个独立集合、天然按库隔离，索引随重启保留；多实例部署时切换共享向量服务即可。
- **模型策略**：平台默认模型 + 按智能体蓝图可覆盖（接智谱 GLM，Anthropic 兼容端点）；凭证集中在内部服务主体下由平台管理员维护，最终用户全程无感知、前端零配置——银行场景模型出口必须集中管控。

### 2.3.4 记忆三层：会话内 / 跨阶段 / 跨项目

| 层 | 载体 | 机制 | 生命周期 |
|---|---|---|---|
| ① 工作记忆 | 会话上下文 | 引擎自动压缩：上下文近窗口阈值时提炼结构化摘要，旧原文卸载到工作区磁盘可捞回 | 单会话 |
| ② 项目记忆（跨阶段交接） | 项目档案表（结构化）+ 工作区记忆文件（智能体自主维护） | 档案摘要由编排层在每次阶段审批后从已批准产物**确定性刷新**（不依赖模型），随启动消息注入下游 | 项目周期 |
| ③ 长期知识（跨项目） | 知识库（按组授权） | 项目结束走沉淀审批入库，新项目检索即受益 | 永久 |

关键认知：**"记忆"和"知识库"是两种东西**——记忆是经验性的（自动捕获、相似度召回），知识库是策划性的（人工维护、有版本、有权限）。项目档案是权威交接依据，不赌任何智能体的自觉。

### 2.3.5 数据模型与数据落点

```
users ──< 组成员 >── groups
  │                        │
  │ (一人多项目,一项目多人)    │ (组级授权)
  ├──< 项目成员 >────┐      │
  │                 ▼      │
  │              projects ──< 项目知识库绑定 >── kbs ──< 知识库授权 >──┘
  │                 │
  │                 ├──< stage_runs(阶段运行) ──< approval_tasks(审批任务)
  │                 │         │
  │                 │         └── session_id → 智能引擎会话（跨系统软引用）
  │                 └──< artifact_versions(产物版本)
  │
  └──(沉淀)── 知识库文档 / 案例库（属于 kbs）
```

核心表分工：`projects`（项目聚合根）/ `stage_runs`（每次阶段执行，round 记退回轮次）/ `approval_tasks`（审批留痕，**银行审计的核心表**）/ `artifact_versions`（产物不可变版本链）/ `kbs` 一族（知识库/组授权/项目绑定）/ `price_items`（价格基准结构化表）/ 追溯四表（见 3.2-②）/ `project_archives`（项目档案）。业务库与引擎库**永不共享表**，只存 ID、不建外键。

**数据落点双层**：工作区 = 过程草稿（智能体写的文档、长期记忆文件、用户上传的原始材料），`artifact_versions` = 权威归档（提交送审时定格的不可变版本）。丢了工作区可从归档恢复；工作区是智能体的工作记忆，归档是业务的事实源。

## 2.4 安全架构：四层防护

| 层 | 机制 |
|---|---|
| **用户层** | JWT 登录（scrypt 口令哈希）+ RBAC（负责人/审批人/成员/观察者）+ 资源 ACL；自助注册自动入默认组，管理员调整部门归属；预留 LDAP/OA 对接 |
| **接入层** | BFF 单一入口，前端永不出网；防腐层收窄为 8 个类型化操作；凭证安全投影——api_key 只活在智能引擎，编排层物理上不可见 |
| **应用层** | 工作区隔离：文档类阶段按项目共享、测试阶段每次运行独立沙箱；HITL 工具确认 + 权限模式；知识库先过滤后检索防泄漏 |
| **支撑层** | 引擎主体收敛 `sys:runtime`（外部用户名永不下沉到引擎）；分布式会话锁（两级互斥，双副本实测，见 2.5）；工作区文件下载走 HMAC 签名链接（短时有效）；状态机三重守卫；审批留痕表 + 产物不可变版本链 |

可见性与操作权分离：**部门（组）决定可见性**（组内成员默认可见组的知识库与项目），**项目角色决定操作权**（谁能提交送审、谁能审批，精确到人）——部门内成员对组内资产的可见性一致，操作权按项目角色区分。

## 2.5 部署架构：双形态 + 多实例

```
形态一 · 云端多实例                        形态二 · 银行内网全离线
  负载均衡                                  全部组件 on-prem
 ├─ 前端静态（CDN）                          ├─ PostgreSQL（业务库 + 引擎库）
 ├─ 网关+编排 ×N 副本（无状态）               ├─ Redis（消息总线/分布式锁）
 └─ 智能引擎 ×N 副本（无状态）                ├─ 模型服务（行内推理 / 智谱网关）
     ├─ PostgreSQL（业务 + 会话）             ├─ 向量索引 / 对象存储（内网部署）
     ├─ Redis（总线 / 锁 / SSE 回放）          └─ 全离线安装包（依赖 wheels + 前端产物
     ├─ 向量库 / 对象存储                        + 从源码构建的框架 wheel，
     └─ 模型服务（行内推理/智谱网关）              目标机零外网安装、零外联）
```

**多实例不是"多起几个进程"——是把一切进程内状态外置**（差异清单节选）：

| 组件 | 单实例 | 多实例（目标形态） |
|---|---|---|
| 消息总线 | 进程内 | Redis 消息总线（跨副本事件转发） |
| 会话运行互斥 | 进程内锁 | **两级分布式锁**（见下） |
| 存储 | 内存/单机 | PostgreSQL（带版本化迁移） |
| 工作区 | 本地盘 | 共享存储或容器沙箱（预览请求可能落在任一副本） |
| 知识库文档 | 本地盘 | 对象存储 |
| 向量索引 | 内嵌本地 | 共享向量服务 |
| SSE 事件流 | 同进程直达 | 任一副本可服务任一会话的流——**负载均衡无需会话粘滞** |

**会话互斥的两级语义（双副本实测）**：同进程双投递 → 409 拒绝；跨副本投递被接受、任务在 Redis 分布式锁后**排队串行**（等锁而非快速失败）。同一会话永远单运行，多人同时驱使同一阶段的智能体在机制上不可能。

**落盘与总线的组件分工**：PostgreSQL 做真相之源（全部业务表 + 会话/消息/知识库元数据，持久、事务、可审计、要备份）；Redis 专职协调层（消息队列/事件回放/分布式锁——短暂、可重建，挂了只影响在途运行、不丢任何持久数据）。两者不合并。

**内网离线包**：在外网机器一键构建（依赖 wheels 全量冻结 + 前端静态产物 + 从源码构建的框架 wheel），连同源码拷入内网后 `--no-index` 完全离线安装，已用全新环境验证可跑通。合规要点：数据不出域（模型端点全部内网）、全量审计留痕、产物可落加密存储。

# 03 主要创新点

## 3.1 业务创新点

**① 全生命周期闭环，而非单点提效**

同一项目从需求到验收一条流水线：上游产物自动注入下游启动消息，退回意见随重开轮次注入。对比"每个环节买一个 AI 工具、人肉在环节之间搬运数据"，平台让数据在系统内流转——需求编号 FR-xx 贯穿到功能点 FP-xx、测试用例 TC-xx、报价行，一次录入全程引用。

**② HITL 人机协同：智能体干活、人把闸门**

微观（对话内工具确认）+ 宏观（阶段产物审批）两层介入，各有分工、互不替代。智能体的产出永远是"待审稿"——没有人点头，流程不流转。这回应了金融场景的核心关切：**AI 可以承担专业劳动，但责任边界必须清晰在人**。

**③ 文档先行、全程可审计**

项目 → 阶段 → 轮次 → 产物四级留痕，产物是不可变版本链，审批人/意见/时间全记录。架构设计先于代码（设计文档是开发的唯一依据），每个决策有出处。造价数字全部可回溯：需求 → 功能点 → 用例 → 报价一条链（见 3.2-②）。

**④ 知识沉淀闭环：项目经验回流组织资产**

阶段产出沉淀项目记忆，项目结束走审批入沉淀库与案例库；下一个项目估算时，历史项目的功能点数、实际工期、实际成本成为参照。把"老法师脑子里的经验"变成"平台上可检索的资产"，人员变动不再等于知识流失。

**⑤ 造价方法论数字化：agents classify, platform prices**

NESMA 估算功能点法落地为提示词契约 + 结构化数据：智能体只负责把需求分类成 ILF/EIF/EI/EO/EQ 五类功能点，加权计数（ILF=7 / EIF=5 / EI=4 / EO=5 / EQ=4）由平台统一给定，费率从结构化价格基准表精确查询。**模型负责理解语义，数字的权威在平台**——把大模型用在它擅长的地方，把确定性留给人可以审计的地方。

## 3.2 技术创新

### 技术创新 1：状态机编排 + kickoff 交接协议，替代 BPMN 引擎与 Agent 自治协作

长周期流程（数月、数百次人机交互）的编排，业内常见两条路：BPMN 工作流引擎，或 Agent 自治协作（智能体互相商量着推进）。我们两条都不走：**两级状态机收敛在一个约 200 行的模块**，配合三张表（阶段运行/审批任务/产物版本）。

- 为什么不放 Agent 自治协作里：流程横跨数月，状态必须落在持久化数据库而非会话上下文；审批人/意见/版本锁定是业务数据不是对话内容；Agent 无状态可重跑，流程状态永不依赖某个会话是否存活。
- **kickoff 交接协议**：每个新会话的启动消息由编排层模板化组装——注入项目档案摘要 + 上游已批准产物 + 本阶段任务说明 + 退回意见（重开轮次时）。跨阶段交接不靠智能体"记得"，靠协议保证。
- 何时才需要 BPMN：审批规则频繁变化、出现会签/条件分支/跨项目编排时再评估——配置化接口已预留，届时把转移规则数据化即可平滑过渡。

### 技术创新 2：追溯矩阵——需求 → 功能点 → 测试用例 → 报价的结构化侧表

造价交付要回答"这笔钱对应哪些需求、哪些功能点、哪条用例验证"，靠事后解析产物文档拼不出来（文档格式随用户要求变化，解析链脆弱）。平台的解法是**在文档产物旁边铺一条机器可读的侧表轨道**：

- **写入（提示词契约）**：四个文档阶段智能体在人读文档之外，往工作区写固定字段的机器可读侧表（需求表/功能点表/用例表/预算表）——字段固定、逐轮可校验；
- **入库（审批钩子）**：审批通过的钩子从工作区收割侧表入四张追溯表；缺文件/坏数据只记警告，**永不阻断审批**；只有已批准数据入库，读侧取每阶段最新已批准轮次；
- **读侧**：项目详情页渲染贯通矩阵——功能点总数（加权合计）、工时合计、每个切片来自哪次运行；需求 → 功能点 → 用例 → 预算行层层可点。

为什么侧表而不是解析文档：侧表是提示词契约的一部分，与"审批通过才入库"的口径天然对齐；配合"agents classify, platform prices"的定价纪律（3.1-⑤），报价表里每个数字都能点到源头。

### 技术创新 3：授权感知检索 + 价格基准双轨

- **先过滤、后检索**：权限判定在编排层完成，不通过的知识库不进入检索候选——防泄漏（不会把无权内容检索出来再过滤）也省算力；
- **价格基准双轨**：数值进结构化表、由 MCP 工具精确查询（端到端走查中预算智能体实调 7 次查准费率，其中一次"某地区无生产率基准"的空结果被提示词约束引导自动回退全国基准——工具异常路径也在验证范围内）；说明性文档才进 RAG。让"检索增强"服务理解、让"工具查询"服务计算。

### 技术创新 4：工作区与沙箱隔离

- **共享工作区目录钉死**：框架默认的工作区目录按智能体解析，跨阶段共享的项目工作区在缓存逐出后会静默断裂。平台以约 30 行的子类把共享目录钉死——同一项目六个阶段的智能体真正共享同一目录，项目记忆与中间产物不断链；未命中约定的目录保持框架默认行为不变；
- **阶段运行级沙箱**：测试阶段每次运行拿独立工作区，与文档阶段的共享工作区物理分开。沙箱边界与"可抛弃状态"的边界一致：运行内环境连续（装好的依赖、测试脚本都在），运行结束归档后回收——干净基线、每次可复现，接近持续集成的 per-run 语义。M6 规划升级为每次运行一个专用容器沙箱——"智能体放手操作、不出乱子"。

### 技术创新 5：不改框架的组装式集成

对开源框架的态度是**组装而不改造**：运行时组装三件套（存储/消息总线/签名密钥）+ 防腐层 + 约 30 行的子类，实现平台的全部增量能力；编排层依赖仅 9 个包、**完全不依赖框架代码包**，与框架之间只有 HTTP 边界。收益：

- **上游升级零冲突**：手工 cherry-pick 纪律、能上游化的补丁提回官方（本地补丁数量 = 升级成本的直接度量，目标趋零）；
- **框架能力原样继承**：分布式会话锁、SSE 回放、权限暂停、上下文压缩等安全与并发能力不需要自己造；
- **代码长期可维护**：框架保持官方形态，平台增量全部收敛在自研层，两套代码各自演化。

| **部署形态** | 多副本智能引擎（同库同总线，编排层多副本地址轮询 + 连接级故障转移）；内网全离线安装包（wheels + 前端产物 + 源码构建的框架 wheel）；md→docx/xlsx 导出服务 | M5 |

> 沙箱真执行（容器化）、会签/多级审批、真实 RAG 全链路挂载在 M6 待办清单，见 §05。

## 4.2 端到端验证

**全六阶段自动化走查（13 分钟跑通）**：以一个虚拟项目完成全流程一次运行，验证三件事——

- **六阶段闭环**：需求 → 原型 → 工时预算 → 测试用例 → 测试 → 验收审计全部走通，**含一次退回重做**（退回意见注入重开轮次）；
- **工具链真实调用**：预算智能体实调价格基准 MCP 7 次查准费率，含空结果自动回退——工具异常路径也在验证范围内；
- **隔离真实生效**：文档阶段共享项目工作区、测试阶段切独立沙箱工作区，同一项目两类工作区物理分开。

**配套验收**：

- 权限与价格基准**十个用例**全过（跨组检索拒绝 / 非管理员导入拒绝 / MCP 精确返回导入值 / 无向量化凭证时创建知识库优雅降级且零落库）；
- 沉淀闭环以真实草稿走完审批入库全流程；
- **多实例实测 11 项全过**：脚本自动拉起第二个引擎副本（同库同总线）——六智能体双副本可见、跨副本会话与事件流、A 副本经共享分布式锁观察到 B 副本的运行、进程内双投递 409、跨副本排队串行后两条回答落库、编排层故障转移（死地址→健康副本）、docx/xlsx 导出、全离线 venv 安装。

## 4.3 预期效益

> 以下为设计目标，量化数据待真实项目运行后由统计看板沉淀（刻意不编数字）：

- **提效**：评估主链（需求结构化 → 功能点计数 → 预算表）从专家人天级压缩到小时级——走查已证明全流程 13 分钟可跑通，真实项目按审批节奏以天计；
- **控险**：报价数字全部可追溯（NESMA 权重平台统一、费率查结构化表），审计取证从"翻文档"变成"查追溯矩阵"；AI 产出全部过人工闸门，责任边界清晰；
- **沉淀**：每个项目自动形成案例档案（功能点数/工期/成本），新项目估算自动参照同类历史——评估准确率随使用量提升，而非随人员经验波动。

# 结语

这个项目想验证的命题很简单：**专业评估类工作可以让智能体承担智力劳动、让人守住责任闸门，且全程数字可溯、经验可沉淀**。六阶段流水线、两层 HITL、追溯矩阵、"agents classify, platform prices"——都是这个命题在造价场景的具体化。

四层分层让职责清晰（门户交互 / 网关中枢 / 业务编排 / 智能引擎），组装而不改造让底座可持续（开源框架保持官方形态，平台增量全部收敛在自研层），里程碑制让交付可验证（每步都有自动化验收）。
