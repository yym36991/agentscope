## 1. 业务全景与目标

**业务域**：银行行业软件造价评估——从需求提出到验收审计的全生命周期管控。单个项目周期以**月**计，贯穿 6 个专业阶段，每个阶段由一个智能体辅助产出，且**必须经人工确认/审批**后才能进入下一阶段。

```
┌────────┐   ┌────────┐   ┌──────────┐   ┌────────┐   ┌────────┐   ┌─────────┐
│①需求生成│──▶│②原型设计│──▶│③工时预算  │──▶│④测试用例│──▶│⑤测试    │──▶│⑥验收审计 │
│ 智能体  │审 │ 智能体  │审 │ 罗盘智能体│审 │ 智能体  │审 │ 智能体  │审 │ 智能体   │
└────────┘批 └────────┘批 └──────────┘批 └────────┘批 └────────┘批 └─────────┘
   PRD         原型         功能点清单/      用例文档      测试报告      结算/审计
              (HTML等)      预算表                       (功能+单元)    汇总报告
              ▲             ▲                                          ▲
              └──── 人工审批不通过则退回当前阶段修订（可多轮）──────────────┘
```

**硬性要求**：

| 要求 | 含义 |
|---|---|
| 多租户 | 用户属于组（部门），组间数据隔离；知识库按组授权 |
| 长周期项目 | 项目持续数月，绝非单个会话能统筹；需要项目 → 阶段 → 会话的层级 |
| 人工审批 | 每阶段闸门，不同阶段可由不同负责人审批，全部留痕（银行审计要求） |
| 双形态部署 | 公有云 K8s 多实例 + 银行内网全离线部署 |
| 会话隔离 | 用户隔离、项目隔离、会话级隔离（并发互斥） |
| 多轮对话与记忆 | 阶段内多轮交互，跨阶段有交接，跨项目有沉淀 |
| 编排能力 | 阶段流程可配置（审批策略、是否自动流转等） |

```
┌──────────────────────────────────────────────────────────────────────┐
│ 前端 SPA（React 19 + Vite，一套代码、两个视图）                          │
│  ┌───────────────────────────┐    ┌─────────────────────────────────┐ │
│  │ 视图A·项目生命周期(类禅道)    │    │ 视图B·Agent工作台(类WorkBuddy三栏)│ │
│  │ 看板/详情/时间线/审批/版本链  │◀──▶│ 左:项目上下文 中:对话 右:产物预览  │ │
│  └───────────────────────────┘    └─────────────────────────────────┘ │
└───────────────────────────────┬──────────────────────────────────────┘
                        HTTPS/JWT│  前端只对接业务编排层（BFF 模式）
┌───────────────────────────────▼──────────────────────────────────────┐
│ 业务编排层 platform-backend（自研 FastAPI）——平台的"控制面"               │
│  用户/组/RBAC · 项目管理 · 阶段状态机 · 审批任务 · 产物版本链              │
│  知识库授权 · 项目档案(跨阶段记忆) · SSE 透传 · 文档导出(docx/xlsx)        │
│  业务库: PostgreSQL                                                   │
└──────┬──────────────────────────────────────────┬────────────────────┘
       │ HTTP（X-User-ID: p:{project_id}）          │
┌──────▼──────────────────────────────────────────▼────────────────────┐
│ 智能体运行时层 agentscope-service（AgentScope）——平台的"执行面"          │
│  6×阶段智能体(AgentRecord) · 会话/上下文压缩 · 工具/技能/MCP             │
│  RAG 检索 · 项目 Workspace(产物落盘) · 长期记忆中间件 · SSE 事件流        │
└──────┬───────────────┬───────────────────┬──────────────┬─────────────┘
       │               │                   │              │
 ┌─────▼─────┐  ┌──────▼──────┐  ┌─────────▼─────┐  ┌─────▼─────────┐
 │ PostgreSQL │  │ Redis       │  │ Qdrant        │  │ 模型服务        │
 │ 会话/智能体  │  │ 消息总线/分布式锁│  │ 向量检索(每KB一库)│  │ vLLM / 智谱GLM │
 │ 记录存储     │  │             │  │               │  │ (OpenAI/Anthropic兼容)│
 └───────────┘  └─────────────┘  └───────────────┘  └───────────────┘
                 MinIO/S3：知识库文档原文 + 产物归档
```

**三条核心原则**（后面所有设计都从这三条推导）：

1. **控制面与执行面分离**。业务流程（谁审批、走到哪步、产物哪个版本有效）是普通工程问题，用普通工程手段（数据库 + 状态机）解决；智能体只负责"阶段内的智力劳动"。不要把业务流程塞进 Agent 的自治协作里。
2. **AgentScope 不直接面向最终用户**。所有前端流量经过业务编排层（BFF 模式）：鉴权、授权、审计、租户隔离全部收敛在一处；AgentScope 退居内网，是编排层的"智能体引擎"。
3. **平台用户体系与 AgentScope 主体解耦**。AgentScope 的 `X-User-ID` 只是运行时主体标识，由编排层按规则映射（见 §8.2），平台的用户/组织/权限体系完全自己持有。

## 3. 前端：一个前端、两个视图

结论先行：**你的"一个前端、两个视图"判断是对的**。不需要部署禅道，禅道只是信息架构的参考范式（仪表盘/列表/详情/审批流），用 React 自研管理视图即可。

### 3.1 视图划分与路由

| 视图 | 主要用户 | 路由（示意） | 内容 |
|---|---|---|---|
| A·项目生命周期 | 项目负责人（项目经理） | `/projects`、`/projects/:id` | 项目看板（卡片显示当前阶段/待审事项/产物数）、项目详情（阶段时间线 + 运行历史 + 成员管理 + 待我审批） |
| A'·审批中心 | 项目审批人 | `/approvals` | 审批收件箱：分配给我的待审任务列表 → 产物内容预览 + 通过/退回；详情里保留一条次级「查看完整对话（只读）」链接，可溯源到负责人与智能体的协作过程 |
| B·Agent 工作台 | 需求提出者、开发人员等与智能体直接交互的人 | `/projects/:id/stages/:stage/chat` | 三栏：左=项目上下文（当前阶段可用智能体/技能/MCP/知识库），中=对话，右=产物预览与下载 |

两视图共享：登录、全局导航、项目上下文（当前项目/阶段）。视图 A 的项目详情页点击"进入 Agent 对话"，携带项目 ID + 阶段上下文跳到视图 B —— 与你草案的设想一致。

**负责人 / 审批人分视角**（v0.5 细化）：同一套导航按操作人角色呈现两个入口——「我的项目」给项目负责人（推进阶段、与智能体协作、提交产物），「审批中心」给审批人（只看待审任务与产物，主操作是通过/退回）。分工依据：

- 审批人在审批详情里**先看产物再下结论**，不被迫翻完整对话；对话链接保留为次级只读入口（先例：钉钉/飞书审批详情的沟通记录、GitHub PR 的 conversation 标签）——审批人对产物有疑问时可溯源，但溯源不参与主流程。
- 审批人由项目成员的 **APPROVER 角色**解析（决策 D8：提交时取首个审批人角色成员，缺省回退到负责人自审，单人流程不受影响）；负责人在项目详情里维护成员表。已在途的审批任务不随成员变动改道。
- 一个用户可以同时是多个项目的负责人和另一些项目的审批人，两个入口都可见；审批中心的角标实时显示待办数。

### 3.2 与现有 web_ui 的关系

现有 `examples/web_ui` 的底子直接复用：

- 技术栈一致：React 19 + Vite + TanStack Query + Tailwind + shadcn 风格组件
- 视图 B 以现有 ChatPage 为基座改造：它已是"侧栏 + 对话区 + 右侧 PanelDock"三区结构（`components/panel/` 已有 KnowledgeBasePanel/McpPanel/SkillPanel/TaskPanel 等），把"会话侧栏"换成"项目阶段上下文"，把 PanelDock 之一固定为"产物面板"即可
- 视图 A 是全新页面，但复用其 UI 组件库与请求层
- **一个关键改动**：现有前端直连 AgentScope（localStorage `server_url` + `X-User-ID`），平台版前端必须改为**只连业务编排层**（JWT 登录），SSE 由编排层透传（见 §8.4）

## 4. 领域模型：人 / 组 / 项目 / 知识库 / 会话

### 4.1 实体关系图

```
users ──< group_members >── groups
  │                            │
  │ (一人多项目,一项目多人)        │ (组级授权)
  ├──< project_members >──┐    │
  │                       ▼    │
  │                    projects ──< project_kb_links >── kbs ──< kb_grants >──┘
  │                       │
  │                       ├──< stage_runs(阶段运行) ──< approval_tasks(审批任务)
  │                       │         │
  │                       │         └── session_id → AgentScope 会话(外部系统)
  │                       └──< artifact_versions(产物版本)
  │
  └──(沉淀)── kb_documents / case_library(案例库, 属于 kbs)
```

### 4.2 核心表（业务库 PostgreSQL，属编排层）

| 表 | 关键字段 | 说明 |
|---|---|---|
| `users` | id, name, email, platform_role | platform_role：平台管理员/普通用户 |
| `groups` | id, name, parent_id | 组（部门），支持树形 |
| `group_members` | user_id, group_id | **用户 N—N 组**（一人可属多组） |
| `kbs` | id, name, kb_type, agentscope_kb_id, owner_group_id | kb_type：行业规范/价格基准/案例/模板/沉淀；`agentscope_kb_id` 指向 AgentScope 侧知识库 |
| `kb_grants` | kb_id, group_id, level(read/write) | **组级授权**；write 可管理文档 |
| `projects` | id, name, status, current_stage, owner_user_id | 项目聚合根，周期以月计 |
| `project_members` | project_id, user_id, project_role | project_role：发起人/项目经理/审批人/成员/观察者 |
| `stage_runs` | id, project_id, stage_type, status, version, agentscope_session_id, agentscope_agent_id | **一次阶段执行**；修订循环复用同一条 run（version 递增）；跨大版本重开新 run |
| `approval_tasks` | id, stage_run_id, artifact_version_id, assignee_user_id, action, comment, acted_at | 审批留痕，银行审计的核心表 |
| `artifact_versions` | id, project_id, stage_type, version, file_path, format, status | status：draft/submitted/approved/superseded |
| `project_kb_links` | project_id, kb_id, stage_type(nullable) | 项目用哪些知识库；**可按阶段绑定**（需求阶段→规范库，预算阶段→价格库） |
| `stage_flow_configs` | project_id(或全局默认), stage_type, approval_policy, auto_advance | 编排能力落点：每阶段谁审批、通过后是否自动流转 |

### 4.3 权限模型：RBAC + 资源 ACL 两层

业内标准做法（GitLab 同款思路），不要发明新模型：

1. **平台角色（RBAC）**：管理员/普通用户 —— 决定"能不能进这个功能"
2. **资源访问（ACL）**：
   - 项目：看 `project_members`（成员才可见）
   - 知识库：看 `kb_grants`（组级授权 + 可选的用户级例外授权表）
   - 权限判断永远发生在**编排层**，AgentScope 侧不做业务权限（见 §8.2）
3. **读写分离**：知识库 read（检索/浏览）与 write（上传/删除文档）分开授权

> 为什么组级授权而非用户级？银行场景部门边界清晰、人员流动频繁，按组授权管理成本最低；用户级只做例外补充（如外聘专家单独开某个库）。

**可见性与操作权分离（v0.2 明确）**——回答“部门内所有成员权限是否一致”：

- **部门（组）决定可见性**：组内成员默认可见组的知识库、组的项目（决定“能看到什么”）
- **项目角色决定操作权**：谁能提交送审、谁能审批、谁只是观察——精确到人（`approval_tasks.assignee`），审批流必须找到具体负责人（决定“能做什么”）
- 即：部门内成员对组内资产的**可见性一致，操作权按项目角色区分**
- 登录映射：新用户自助登记 → 自动落入默认组 `default` → 管理员调整部门归属（预留 LDAP/OA 对接后从目录自动带出）

## 5. 流程引擎：业务状态机与人工审批

### 5.1 你的判断是对的：用状态机，不用 Agent 自治协作

三个理由：

1. **周期错配**。AgentScope 的 Team 机制（leader 派发 AgentCreate + TeamSay 消息传递）为"单次任务内的多智能体协作"设计；而我们的流程横跨数月、数百次人机交互，状态必须落在**持久化数据库**里，而非某个会话的上下文里。
2. **人工闸门是一等公民**。审批人、审批意见、版本锁定、退回修改——这些是业务数据不是对话内容；状态机 + `approval_tasks` 表天然留痕，满足银行审计。
3. **Agent 无状态可重跑**。任何阶段的智能体崩溃/换模型/重跑，都不影响流程状态；流程状态也永远不依赖某个会话是否存活。

### 5.2 两级状态机

**项目级**：`DRAFT → ACTIVE → ACCEPTED → ARCHIVED`（外加 `SUSPENDED`/`CANCELLED`）

**阶段级**（每个 stage_run 一个实例，核心）：

```
                    ┌─────────────┐
   上一阶段 APPROVED │ NOT_STARTED │
        ───────────▶│   未开始     │
                    └──────┬──────┘
                           │ 启动（按配置：自动 / 项目经理手动）
                           ▼
                    ┌─────────────┐   提交产物送审
                    │ IN_PROGRESS │──────────────────┐
     退回修改 ◀───── │ 人机协作中   │                  ▼
     （附审批意见）   └─────────────┘           ┌──────────────┐
           │                                 │ UNDER_REVIEW │
           │        重新协作修改                │   待审批      │
           └──────────────────────────────── └──────┬───────┘
                                          审批通过    │ 审批驳回(退回)
                                                  ▼
                                          ┌──────────────┐
                                          │   APPROVED   │──▶ 下一阶段待开启
                                          │   已通过      │
                                          └──────────────┘
```

要点：

- **IN_PROGRESS 就是"人机协作中"**——不是批处理任务在跑。智能体在会话里多轮交互，用户认为产物成熟了才点"提交送审"
- **审批 ≠ 开启 ≠ 开始（三段式，v0.5）**：审批通过只推进 `current_stage`，不开新 run；「开启」由人点按钮、只建运行（纯 DB，智能体不动）；运行会话的**首条消息**才是「开始」——编排层把它组装为启动消息（`build_kickoff`：按阶段顺序注入全部上游已批准产物 + 退回意见 + 用户开场白/附件），智能体才动工。这样审批人与开启人可以是不同角色，且开启后有窗口补充材料（如工时预算阶段上传外部模型产出的《功能点明细》xlsx）
- **退回修改 = 同阶段新 run（round+1）+ 全新会话**：启动消息注入审批退回意见与上游产物；上一轮草稿仍在共享 workspace 可供重读
- **并发互斥**：AgentScope 对每个会话有分布式运行锁（同一 session 同时只允许一个 run，`POST /chat/` 冲突返回 409）——天然防止两个人同时驱使同一阶段的智能体
- **每次状态转移写一条转移日志**（who/when/from/to/comment），审计兜底

### 5.3 与"对话内确认"的分工（容易混淆，明确一下）

平台里有两层"人机确认"，**不要互相替代**：

| 层 | 机制 | 用途 |
|---|---|---|
| 对话内确认（微观） | AgentScope 的 `AskUser` 工具、工具权限确认卡（HITL 卡片，前端已有 `SubagentHitlCard`/`ConfirmCard`） | 智能体干活途中的即时确认："要覆盖这个文件吗？""这个功能点分类对吗？" |
| 阶段审批（宏观） | 编排层状态机 + `approval_tasks` | 阶段产物是否合格、能否进入下一阶段——**这才是你要的"人工参与"** |

### 5.4 要不要上 BPMN 工作流引擎（Activiti/Camunda/Flowable）？

**初版不要**。6 阶段线性流 + 退回循环，用代码化状态机（枚举 + 合法转移表 + 转移日志）200 行搞定，可读可测。**何时引入**：审批规则频繁变化、出现会签（多人同时审）/条件分支/跨项目流程编排需求时，再评估——`stage_flow_configs` 表已经为"配置化"留了口子，届时把状态机的转移规则数据化即可平滑过渡。

## 6. 会话与记忆设计

### 6.1 层级映射：项目 → 阶段运行 → 会话（你问的"要不要引入项目 id、多个 session"）

**要，而且必须**。先澄清一个代码事实：**AgentScope 没有 thread 概念，会话（session）就是唯一对话单元**（`UserRecord → AgentRecord → SessionRecord` 三级）。所以平台自己定义层级，把 AgentScope 的 session 挂在最末级：

```
项目 project（月级，编排层实体，AgentScope 无此概念）
 └─ 阶段运行 stage_run（天~周级，修订循环内 version 递增）
     └─ AgentScope session（一次连续的人机协作对话，多轮消息）
         └─ 消息/上下文（AgentScope 自动压缩管理）
```

规则：

| 场景 | 做法 |
|---|---|
| 阶段开启 → 工作台首条消息 | 「开启」只建运行；会话在首条消息时懒创建，且该消息被编排层组装为 kickoff：注入全部上游已批准产物 + 退回意见（如有）+ 用户开场白/附件（`build_kickoff`，见 6.3） |
| 退回修改 | 新 run（round+1）+ 全新 session，kickoff 注入退回意见；上一轮草稿留在共享 workspace |
| 大版本重开（数月后重做/范围大变） | 新建 session（stage_run 新 run），kickoff 注入结构化交接摘要 |

### 6.2 三层记忆（对齐业内 working memory / episodic / semantic 分层）

| 层 | 载体 | 实现机制（AgentScope 现成能力） | 生命周期 |
|---|---|---|---|
| ① 工作记忆 | 会话上下文 | `AgentState.context` + `ContextConfig`：上下文达 80% 自动压缩为结构化摘要（任务概览/当前状态/重要发现/待办），工具结果超限截断，旧图片卸载到 workspace | 单会话 |
| ② 项目记忆（跨阶段交接） | 双份：a) 编排层**项目档案表**（结构化：需求摘要/关键决策/预算口径/产物索引）；b) AgentScope **`AgenticMemoryMiddleware`**（项目 workspace 下的 MEMORY.md，智能体自主记录/检索） | a) 每次阶段 kickoff 由编排层注入 system 上下文；b) 中间件挂载即用 | 项目周期 |
| ③ 长期知识（跨项目共享） | 知识库（按组授权） | AgentScope KB + `RAGMiddleware`（会话绑定的 KB 自动检索注入） | 永久，按组维护 |

关键认知：**“记忆”和“知识库”是两种东西**。记忆是经验性的（自动捕获、相似度召回、无需审核）；知识库是策划性的（人工维护、有版本、有权限）。项目档案（②a）是权威交接依据——不依赖任何智能体的自觉。

**部门（组）级不设记忆层（v0.2 明确）**：部门级的积累沉淀一律走知识库（策划性、人工审核、有版本与权限）；记忆只存在于会话级（工作记忆）与项目级（项目记忆）——经验性、自动捕获。

### 6.3 阶段交接（kickoff）协议

每个阶段的 kickoff 消息由编排层**模板化组装**，保证下游智能体的输入确定性：

```
[项目档案摘要]  ← 项目档案表渲染（需求关键点、既有决策、预算口径…）
[上游产物]      ← 引用 project workspace 中的文件路径 + 版本号
[本阶段任务]    ← 阶段任务模板 + 审批意见（若是退回修改）
[知识库提示]    ← 本阶段绑定的 KB 已通过 RAG 中间件挂载，无需显式传内容
```

### 6.4 知识沉淀闭环（项目 → 组织资产）

```
⑥验收审计 APPROVED
   → 沉淀流程（可配置为人工触发或自动起草）：
     编排层调用一个"沉淀智能体"（或固定流水线）提取：项目案例/功能点系数偏差/常见问题
   → 人工审核（同样走 approval_tasks）
   → 脱敏后写入所属组的"沉淀库"（kb_type=沉淀）
   → 此后所有该组的新项目在 RAG 检索中受益
```

沉淀库与案例库的分离：案例库（结构化项目档案检索）服务预算阶段找相似项目；沉淀库（经验教训）服务全阶段。

## 7. 知识库体系与权限

### 7.1 知识库分类（kb_type）

| 类型 | 内容 | 形态 | 主要消费阶段 |
|---|---|---|---|
| 行业规范库 | 银行监管文件、软件工程规范、造价标准（如功能点计数规范） | 文档 RAG | ①④⑥ |
| 价格基准库 | 功能点单价、地区系数、人月费率 | **结构化表 + 文档** | ③ |
| 案例库 | 历史项目档案（功能点数/实际工期/实际成本） | 结构化 + RAG | ③⑥ |
| 模板库 | PRD 模板、测试用例模板、审计报告模板 | 文档 | ①②④⑥ |
| 沉淀库 | 项目经验、系数修正、常见问题 | 文档 RAG | 全阶段 |

> 价格基准库建议**双轨**：核心数值（单价/系数）放业务库结构化表（③的预算智能体用工具精确查询，保证计算确定性），说明性文档走 RAG。**不要把费率表扔进向量库让模型"检索着算"**——造价场景数字必须可审计。

### 7.2 权限执行点（全部在编排层）

```
用户发起检索/上传
  → 编排层: 用户 ∈ 哪些组? → 可见 KB 集合 = Σ kb_grants(组) ∪ 用户例外授权
  → 阶段可用 KB = project_kb_links(本阶段) ∩ 可见集合
  → 编排层以内部主体代理调用 AgentScope KB API（检索/挂载到会话）
```

- **先过滤、后检索**（authorization-aware RAG）：权限不通过的知识库根本不进入检索候选，而不是检索完再过滤（防泄漏 + 省算力）
- AgentScope 侧每个 KB 物理独立一个向量集合（`CollectionPerKbManager`，`kb_<uuid>`），天然按库隔离
- 文档上传/删除 = write 权限，仅授予管理组

### 8.2 主体映射（关键设计，纠正一个常见误区）

AgentScope 的一切资源以 `X-User-ID` 为主体归属（user 级隔离是有的，**但没有组/租户级**）。平台的映射规则：

| 平台身份 | AgentScope 主体 | 用途 |
|---|---|---|
| 服务身份 | `sys:runtime`（**唯一运行主体**） | **6 个全局智能体、平台知识库、全部项目会话与 workspace 都挂在这个主体下** |
| 个人用户（可选，后期） | `u:{user_id}` | 个人助理等与项目无关的对话 |

> v0.2 修订说明：v0.1 曾设计“每项目一个虚拟主体 `p:{id}` + 每项目克隆 6 个智能体”。修订为**单一运行主体 + 全局共享智能体**（理由见 §8.3）。项目/阶段的归属映射由编排层 `stage_runs` 表维护 `(project, stage, version) → (agent_id, session_id, workspace_id)`——AgentScope 侧无需感知“项目”概念。

为什么不用个人主体：同一阶段的协作与审批需要多人看到**同一段对话**，而 AgentScope 会话按主体隔离（A 的会话 B 天然不可见）。会话挂服务主体后，“谁能看哪个会话”完全由编排层判断后透传——**可见性规则只有一个真相来源**。

> 纵深防御演进路径（暂不做）：若后续需要 AgentScope 层面的项目隔离，引入“每项目主体 + `ResourceAccessPolicy`”（框架有此插拔点，默认全拒绝），不影响其他设计。

模型凭证：平台管理员在 `sys:runtime` 下配置模型凭证（内网 vLLM / 智谱 GLM——本机已跑通 Anthropic 兼容端点），**不对最终用户开放**——银行场景模型出口必须集中管控。模型按会话配置（AgentScope 本来就是 per-session 的 `chat_model_config`），编排层在创建会话时按“平台默认 + 智能体蓝图覆盖”解析写入（见 §8.6）。

### 8.3 六个阶段智能体：全局共享一套（v0.2 修订）

先纠正草案的一个技术点：**SubAgentTemplate 不是用来注册阶段智能体的**——它是 Team 机制的“孵化配方”（leader 智能体在会话里用 `AgentCreate` 工具动态拉起子智能体时使用）。阶段智能体是长期存在的智能体**定义**，用 `POST /agent/` 创建 `AgentRecord`。

**采用：全局共享 6 个智能体（挂在 `sys:runtime` 下），项目创建时零智能体创建。**

为什么共享是安全的（也是业内的统一做法）：**智能体定义是无状态的，上下文不挂在智能体上，而挂在会话上**。AgentScope 中 `AgentState`（完整上下文 / 摘要 / 工具缓存）属于 `SessionRecord`——同一个智能体开 100 个会话，各会话的上下文互不可见、互不污染。“一个智能体服务多个项目、多个 session”**不会**导致上下文混乱，这是机制保证，不是概率上的“一般不会串”。

业内参照：OpenAI Assistants（一个 assistant 服务无数 thread）、Dify（一个 App 服务无数会话）、Coze（一个 Bot 多会话）、LangGraph（一份图定义、多 thread 状态）——全部是“**定义共享、状态随会话**”。

| | 全局共享（采用） | 每项目克隆（v0.1 方案，废弃） |
|---|---|---|
| 记录数 | 固定 6 条 | 6 × 项目数 |
| 提示词升级 | 改 1 处，全局生效 | 逐项目迁移，版本漂移 |
| 项目隔离 | 会话 + workspace + L1 网关 | AgentRecord 归属 |
| 按项目定制 | kickoff 注入增量上下文 | 直接改克隆的提示词 |

配套机制（与 §8.2 呼应）：

- 会话区分：`(sys:runtime, 阶段智能体, 项目 workspace)` 三元组在 AgentScope 内天然唯一——**同一项目同一阶段有且只有一个会话**，退回修改天然续用；“大版本重开”通过项目版本 v+1（新 workspace）实现，上游已审产物由 L1 经 kickoff 注入（§8.5）
- 真正会导致上下文混乱的是“多个项目共用同一个 session”——平台映射规则（一个项目一个阶段一个 session）从根上排除
- 按项目个性化：不做克隆，用“基础提示词 + 项目增量上下文”在 kickoff / 系统上下文注入（如某分行的特殊口径）
- 何时才值得克隆：合规要求“不同分行提示词物理隔离”这类硬场景——届时再评估
- SubAgentTemplate 保留给**阶段内部**的子任务孵化（如需求生成智能体孵化只读“探索员”处理大文档——仓库示例里的 explorer 模板就是这个用法，有现成参考）

### 8.4 一次阶段协作的完整时序

```
用户(视图B)          编排层L1                    AgentScope
   │ POST /stage-run/{id}/message  │                    │
   ├──────────────▶│ 鉴权: 是项目成员? 阶段 IN_PROGRESS?  │
   │               │ POST /chat/ {agent_id, session_id, input}
   │               ├───────────────────▶│ 分布式锁获取(run 开始)
   │               │◀─── {status:started}│
   │ 202           │                    │ 智能体推理/工具/RAG…
   │               │ GET /sessions/{sid}/stream?after=cursor
   │◀═════════ SSE 事件透传(增量消息/工具卡/HITL确认卡) ═════│
   │               │                    │
   │ 用户点"提交送审"(视图A/B) │            │
   ├──────────────▶│ 快照 workspace 产物 → artifact_versions
   │               │ 状态机 IN_PROGRESS→UNDER_REVIEW, 生成审批任务
   │  审批人(视图A) │                    │
   ├──────────────▶│ APPROVED → 驱动下一阶段: 创建/复用 session,
   │               │   组装 kickoff(项目档案+上游产物+任务) 
   │               │   POST /chat/ 触发下一阶段智能体首轮产出
```

要点：kickoff 也是一次 `/chat/` 调用——下游智能体的首轮产出是"被流程驱动"的，用户进会话时往往已有初稿可改。

### 8.5 产物落盘与传递（修正草案的 workspace 论述）

草案说"产物传递通过 Workspace 机制"——方向对，落点是：**一个项目一个 workspace**（阶段间共享），目录约定：

```
project-workspace/
├── 01-需求生成/   prd-v1.md, prd-v2.md, ...
├── 02-原型设计/   prototype-v1.html, ...
├── 03-工时预算/   function-points-v1.md, budget-v1.xlsx...
├── .../
├── uploads/       用户上传的原始文档(需求文件等)
└── MEMORY.md      项目级长期记忆(AgenticMemoryMiddleware 自动维护)
```

- 智能体用内置 Write/Edit 工具写文件（前端已有对应渲染器，体验成熟）
- 提交送审时编排层经 `/workspace/files` 拉取快照存入 `artifact_versions`（版本定格，后续修改不影响已审版本）
- 需要核实的小点（实现时验证）：`POST /sessions/` 能否显式指定 `workspace_id`（SessionConfig 含该字段）；若不能，退路是自定义隔离策略（按项目分配 workspace）或 PER_SESSION 策略 + 编排层归档注入——**`artifact_versions` 才是权威归档，workspace 只是工作区**，丢了可从归档恢复
- **同一项目同一阶段会话唯一**（(主体, 智能体, workspace) 三元组约束，v0.2）：退回修改天然续用同一会话；“大版本重开”通过项目版本 v+1（新 workspace）实现
- **workspace 按阶段分配（v0.3 统一规则）**：文档类阶段 = `proj-{project_id}`（项目版本重开时 v+1）；测试阶段 = `test-run-{stage_run_id}`（专用沙箱，见下）——workspace_id 由 L1 写入 `stage_runs` 映射表

**测试阶段的专用沙箱（v0.3 决策：真执行 + 阶段运行级粒度）**

⑤测试智能体要真正执行测试（跑 Bash / 装依赖 / 执行测试框架），它的会话**不共用项目 workspace**，而是每次阶段运行分配一个专用沙箱 workspace（`test-run-{stage_run_id}`，用 `DockerWorkspaceManager`，每个 workspace 对应一个容器）：

- **粒度判断标准：沙箱边界应与“可抛弃状态”的边界一致**
  - 项目级沙箱 ✗：跨 session 累积环境残留——依赖冲突、缓存膨胀、上次跑挂的现场，测试不可复现（“这用例为什么在我这就跑不过”无解）
  - 阶段运行级 ✓（一次 stage_run 一个沙箱）：session 内环境连续（装好的依赖、venv、测试脚本都在，改了用例重跑无需从头装环境），运行结束归档后销毁——干净基线、每次可复现；接近 CI 的 per-run 语义，又避免 per-turn 的过度碎片化
- **生命周期**：阶段启动 → L1 创建沙箱 workspace → 注入源码（用户上传的源码包先归档 `artifact_versions`，再注入沙箱）→ session 内多轮“改用例 → 跑 → 看结果”（环境连续）→ 提交送审 → 快照测试报告 / 日志 / 测试脚本入 `artifact_versions` → 沙箱回收（可配置保留 N 天供排障）
- 其他五个文档类阶段仍用项目 workspace——它们只写文档，无环境状态，不需要沙箱开销
- 冷启动优化：`PrewarmConfig` 容器预热；内网 Docker 镜像离线预装（Python + 常用测试框架基础镜像）；本地开发机需要 Docker Desktop

### 8.6 模型配置：平台默认 + 按智能体覆盖（v0.2 决策）

```
配置链:  平台默认模型 ──覆盖──▶ 智能体蓝图级模型 ──(未来)──▶ 项目级覆盖
落点:    L1 创建/更新阶段会话时, 解析配置链写入
         SessionConfig.chat_model_config (credential_id + model + 参数)
         —— AgentScope 的模型本来就是按会话配置的, 正好承接
用户侧:  全程无感知——不见凭证、不见模型选择, 前端零配置
```

例：平台默认 GLM-5.3；预算罗盘智能体配置覆盖为推理更强的模型——只有它换，其余五个仍用默认。凭证集中在 `sys:runtime` 下由平台管理员维护，最终用户不可见。

### 8.7 开源框架的升级兼容策略（v0.4）

原则：**接触面最小化、集中收口、契约测试把关**。兼容性问题的本质是耦合面管理——三层架构已经完成了最关键的一步：L1 与运行时之间是 **HTTP 边界**（网络接口是最容易做版本化的耦合形式），而非库级 import。

**耦合面盘点与对策**：

| 耦合点 | 程度 | 对策 |
|---|---|---|
| HTTP API（L1→运行时：chat / sessions / agent / KB / workspace / SSE） | 主要耦合 | 防腐层单模块收口 + 契约测试 |
| 服务组装（运行时 main.py 的 `create_app` 参数） | 低 | 单文件、显式声明，升级对照 changelog 调整 |
| 框架源码补丁（anthropic auth_token 修复、GLM 模型卡） | 最麻烦 | 补丁纪律（见下） |
| 存储结构（`AsyncSQLAlchemyStorage` 的 alembic 迁移） | 数据层 | 升级窗口内执行，先 staging 演练 |
| web_ui 前端复用 | 高（平台侧会大改） | 一次性收割，不做活体 fork |

**五个机制**：

1. **防腐层（ACL，Anti-Corruption Layer）**：L1 对运行时的全部调用（含 SSE 解析、`X-User-ID` 传递）收敛到唯一的 `runtime_client` 模块；L1 的领域模型用自己的 DTO，**不 import 任何 agentscope 类型**。上游改接口，只改这一个模块。
2. **契约测试**：把 L1 实际依赖的运行时行为写成测试套件（建智能体 / 建会话 / 触发 chat / SSE 事件序列 / KB 检索 / workspace 下载令牌 / 409 运行互斥…）。CI 对锁定版本跑，升级候选版本先跑它——**上游行为变更时，先红的是测试，不是生产**。
3. **版本锁定 + 升级窗口 + 兼容矩阵**：锁精确版本不追新；按季度或按需（安全修复 / 新特性）升级；固定流程：读 changelog → 契约测试 → staging 迁移演练 → 升级。L1 与运行时独立发版，声明兼容矩阵（L1 1.x ↔ runtime 2.y），L1 启动时校验运行时最低版本。
4. **补丁纪律**（黄金法则：**本地改动越少，升级越便宜**）：
   - 动手改源码前先找扩展点——`create_app` 的插件参数（custom_subagent_templates / extra_middlewares / resource_access_policy / workspace_manager…）能覆盖的绝不改源码
   - 必须改的，一条 commit 一个意图、信息清晰——rebase 到新版本才是机械操作
   - **能上游化的提 PR**（anthropic auth_token 修复对官方仓库就是合理贡献），合并后删除本地补丁；本地补丁数量 = 升级成本的直接度量，目标趋零
   - 模型卡是数据文件，冲突风险低，可随上游自然合并
5. **前端一次性收割**：web_ui 前端在 M1 整块提取进平台前端仓库，之后独立演化；上游后续改进（如新工具渲染器）按需手工 cherry-pick——前端活体 fork 的合并摩擦远高于其价值。

**仓库结构（v0.4 建议）**：平台代码（L1、前端、部署编排、设计文档）放**独立仓库**；本 fork 只保留“框架 + 最小补丁 + 模型卡 + 运行时组装文件”。理由：fork 的职责是贴着上游走、保持最小 diff，混入会持续增长的平台代码会让每次同步上游都变难；且 L1 与运行时本来就是独立发版的两个服务，**仓库边界应与部署边界一致**。

**要盯的上游信号**（当前已知）：代码注释明确 `X-User-ID` 是临时身份方案、将来换 JWT 认证——届时 `runtime_client` 需适配。每次升级先读 release notes 的 breaking changes。

**当前待办**：① 把现有混合提交（框架补丁 + 平台文档/脚本混在一条 "test" 提交里）拆分为按意图分组的干净提交 ② 为 fork 配置 upstream remote 指向官方仓库 ③ anthropic auth_token 修复整理后向官方提 PR

## 9. 产物管理与版本链

- **版本模型**：`artifact_versions` 记录每次送审快照（stage、version、file_path、format、status）。同一阶段多次退回修改 = version 递增；APPROVED 的版本被 superseded 需走变更流程

## 10. 部署架构

### 10.1 公有云（K8s，多实例）

```
                    Ingress/LB
        ┌──────────────┼───────────────┐
   前端静态        编排层×N副本      agentscope-service×N副本
  (CDN/OSS)      (FastAPI,无状态)    (无状态; 专用worker可分拆:
        │              │               index/channel/scheduler 开关)
        │         ┌────┴────────────────────┐
        │         ▼                         │
   PostgreSQL(业务库+会话库)   Redis(消息总线/分布式锁)
   Qdrant(向量)  MinIO/S3(KB文档blob)  共享存储或K8s工作区(产物)
        模型服务: vLLM/OpenAI兼容网关 或 智谱API(Anthropic兼容)
```

多实例要点（全部有现成支撑，已核实）：
- 消息总线必须 `RedisMessageBus`（InMemory 版仅单进程）
- 存储用 `AsyncSQLAlchemyStorage`（PostgreSQL，带 alembic 迁移）
- LB 后必须设置 `download_secret`（文件下载令牌跨实例签名）
- 运行锁是分布式的（Redis 总线），多副本安全

### 10.2 银行内网（全离线）

同一套代码，换成 on-prem 组件：PostgreSQL/Redis/Qdrant/MinIO 均内网部署；模型走**行内推理服务**（vLLM 起开源模型，OpenAI 兼容端点；或行内采购的 GLM 等的兼容网关）；模型卡片 YAML 离线导入（本机已验证 GLM 卡片 + Anthropic 兼容端点这条路）；沙箱工作区用 DockerWorkspaceManager（测试智能体跑测试需要）；离线安装包（镜像 tar + pip/pnpm 离线源）。

合规要点：数据不出域（模型端点全部内网）、全量审计日志（状态转移日志 + 审批表导出）、产物落存储加密。

### 10.3 单实例 vs 多实例：完整差异清单（v0.2 补充）

单实例不只是“少个 Redis”——差异是系统性的：**多实例 = 把一切进程内状态外置**。

| 组件 | 单实例（≈当前本机形态） | 多实例 |
|---|---|---|
| 消息总线 | `InMemoryMessageBus`（仅单进程内有效） | `RedisMessageBus`（Redis Streams + Lua） |
| 会话运行互斥锁 | 进程内锁 | **必须走总线的分布式锁**——否则两个副本可同时驱动同一会话（409 互斥失效） |
| 会话/智能体存储 | `RedisStorage`（外部 Redis，本身可共用） | 同左可用；生产建议 `AsyncSQLAlchemyStorage`(PostgreSQL，带 alembic 迁移) |
| Workspace | `LocalWorkspaceManager` 本地盘即可 | 本地盘须换**共享存储**（NFS/云盘）或沙箱型（Docker/K8s）——产物预览/下载请求可能落在任一副本 |
| 知识库文档 blob | `LocalBlobStore` | `S3BlobStore`（MinIO/S3） |
| 向量库 | 内嵌 Qdrant（`:memory:`，重启即失） | Qdrant 服务（或 Milvus/ES/Mongo，rag 层已有多客户端） |
| 文件下载令牌 | 无需 | **LB 后必须设 `download_secret`**（跨副本签名校验） |
| 后台 worker | 与 HTTP 同进程 | `enable_index_worker / enable_channel_worker / enable_scheduler` 分拆为专用 worker 部署 |
| SSE 事件流 | 同进程直达 | 任一副本可服务任一会话的流（事件走总线订阅）——**LB 无需会话粘滞** |
| 编排层 L1 | 单副本 | 无状态多副本 + PostgreSQL |
| 运维代价 | 简单；单点故障；只能垂直扩展 | K8s 编排、数据库迁移、监控告警、滚动升级 |

注意 Redis 总线不只是“共享队列”：它还承担**事件日志回放**（SSE 断线续传的游标语义）、**分布式锁**（会话单运行互斥）、注册表与收件箱——所以多实例的第一张骨牌是它，但不是唯一一张。

v0.3 决策：**目标形态直接定为多实例**（§13.1 #12）——按多实例的组件约束开发（总线/存储/工作区/blob/向量库全部外置），交付与验证按多实例做；本地开发跑“伪多实例”（组件全部外置、各服务 1 副本，见 §10.5）。“单实例”仍可作为小微内网客户的降级交付选项保留在配置层。

### 10.4 隔离层次总览

| 层次 | 机制 | 在哪实现 |
|---|---|---|
| 用户隔离 | JWT 登录 + RBAC | 编排层 |
| 项目隔离（租户级） | 项目主体 `p:{id}` + 会话/智能体/workspace 挂项目主体 + 项目成员 ACL | 编排层 + AgentScope 主体映射 |
| 会话隔离 | AgentScope 按 (user, agent, workspace) 唯一 + 分布式运行锁（并发 409） | AgentScope（现成） |
| 知识库隔离 | 每 KB 独立向量集合 + 组授权先过滤后检索 | AgentScope（物理）+ 编排层（授权） |

### 10.5 落盘与总线的组件分工（v0.3 决策：PG 落盘 + Redis 总线，不合并）

问题：能否只用 PostgreSQL，把消息总线也做在 PG 上，省掉 Redis 组件？

结论：**拆开两个**。PostgreSQL 做落盘（AgentScope 侧换用 `AsyncSQLAlchemyStorage`，与 L1 业务库同实例不同 schema/库），Redis 专职消息总线与分布式锁。

| | PostgreSQL（真相之源） | Redis（协调层） |
|---|---|---|
| 承载 | AgentScope 会话/消息/智能体/KB 元数据 + L1 全部业务表 | 消息总线（队列 / 事件日志回放 / 收件箱）、会话运行锁、注册表 |
| 状态性质 | 持久、事务、可审计、要备份 | 短暂、可重建 |
| 故障语义 | 挂了 = 停服（从备份恢复） | 挂了 = 在途运行失败、锁释放、用户重试，**不丢任何持久数据** |

不把总线做上 PG 的三个理由：

1. **`RedisMessageBus` 是框架现成的，并被官方注释明确指定为多进程/生产推荐**（examples/agent_service/main.py:77-86，上游示例保持零改动；平台的实际组装入口在 `examples/platform_agent_service/main.py`）；PG 版总线**仓库里不存在**，要自研——而它是并发关键组件（等价于把 Redis 版的 Lua 原子操作换成 `SELECT ... FOR UPDATE SKIP LOCKED` + advisory lock + `LISTEN/NOTIFY` 唤醒 + 轮询兜底），开发测试成本高，且出 bug 的地方恰恰最隐蔽（丢唤醒、重复投递、锁超时）
2. **事件流是高频小消息**（对话/工具/流式事件），走内存队列低延迟；落 PG 则每条事件一行——WAL 写放大 + 热队列表 vacuum 压力，用 OLTP 引擎做消息管道是逆着它的性子
3. **Redis 的部署负担被高估了**：单二进制、无依赖、离线安装极简（本机开发已在用便携版）；银行内网普遍已有 Redis，不构成额外评审负担。组件数量上 PG+Redis=2 并不比 PG-only=1 多出实质运维——省掉的只是一个 5MB 的进程，换来的是自研一个并发关键件

逃生舱（仅在行内硬性规定“只允许 PostgreSQL 一个中间件”时评估）：自研 `PgMessageBus`——事件表 + SKIP LOCKED 消费 + advisory lock 会话锁 + LISTEN/NOTIFY 唤醒。技术上可行（pgmq / graphile-worker / river 等先例），但要接受吞吐上限与长期自研维护成本，**不作为默认架构**。

本地开发环境（v0.3）：

- 目标是多实例，但**本地不跑多副本**——只要进程内状态全部外置（PG 存储 + Redis 总线 + 外部 Qdrant + MinIO），代码就是多实例兼容的；本地各服务 1 副本即“伪多实例”，真 N 副本留到部署验证阶段
- 本机待装：PostgreSQL（便携版免管理员，与 Redis 同方式）；AgentScope venv 需补装 `sql` extra（sqlalchemy/asyncpg/alembic）才能用 `AsyncSQLAlchemyStorage`
- 测试沙箱在本机需要 Docker Desktop（M2 前装即可，不阻塞 M1）
