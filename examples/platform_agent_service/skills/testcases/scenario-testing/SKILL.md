# 场景法

## 何时使用

- 功能点本质是**跨环节的业务流程**（申请→审核→放款→还款；采集→校验→入账→对账），而不是单点输入校验（那种交给[[equivalence-partitioning]]）；
- 需要验证「链条完整性」：上游产出被下游正确消费、状态在环节间正确传递、异常环节可回退或补偿。

## 方法要点

1. **画流程图**：从需求中识别基本流（happy path，一切正常的最短路径）与备选流（每个判定分支、每种异常：校验失败、超时、对方系统拒绝、余额不足…）。
2. **场景 = 基本流 + 若干备选流的组合路径**，逐条编号：
   - 场景 1：基本流（全流程走通）——**优先级最高，必测**；
   - 场景 2..n：基本流中途拐入某个备选流（每个备选流至少被一个场景覆盖）；
   - 关键异常组合：两个备选流叠加（如「审核通过但放款通道超时」）。
3. **每场景一条用例**：操作步骤按路径逐步展开（步骤数=路径长度），预期结果写**每个环节的可见变化**（页面提示、状态变化、落库结果、通知触发），不只写最终结果。
4. 用例说明标注路径（如「基本流 + 备选流 3」），评审可核对每条备选流已被覆盖。

## 银行示例

功能点：提前还款申请。

- 基本流：登录 → 选贷款 → 查提前还款试算 → 确认申请 → 扣款成功 → 状态=已结清；
- 备选流：①当日已提交过申请 ②试算金额>剩余本金 ③卡内余额不足 ④日间批量扣款失败(日终重试)。

场景用例：
- TC-01 场景1 基本流（每步预期：试算页显示违约金→申请成功页→流水落库→状态流转）；
- TC-02 场景=基本流+③：确认申请时提示「卡内余额不足」，贷款状态不变，无扣款流水。

## 提醒

- 流程图的备选流清单要与需求的非功能约束（超时、并发、幂等）交叉核对，缺失的异常路径先向需求方澄清，再进用例；
- 场景法覆盖「链路」，单点取值细节仍需等价类/边界值补充——两者配合而非互斥。
