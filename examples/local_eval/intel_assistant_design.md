# 公开信息简报助手 — 应用设计说明

基于 AgentScope 的多智能体应用。用户打开浏览器即可使用，不需要调接口、不需要写代码。

本次只做这一个助手：**公开检索 + 摘要**，产出带来源链接的简报。不限定竞品，也不做法务合规审查。

---

## 一、这个助手是干什么的

同事用大白话提出想了解的对象或问题，Leader 多轮澄清后邀请专家，先检索公开网页，再归纳成一份简报。

公司动态、行业新闻、招聘口径、公开政策原文、财报披露、召回公告，只要是搜索引擎能打开的页面，都问这一个入口。区别只在 Leader 问清「查谁、查哪几面、查多久」，然后把任务派给同一对专家。

**专家花名册**（常驻，可单独咨询，也可被 Leader 拉进团队）

1. **信息检索** — 挂载搜索引擎 MCP，获取公开实时信息，返回带链接的事实条目
2. **情报提炼** — 把检索结果归纳成要点、变化点和影响评估（只总结，不检索）

```
用户 ──HTTP──► Leader【公开信息简报助手】
              （多轮澄清：关注对象、关注角度、时间范围、用来干什么）
                ① Worker【信息检索】：公开网页 + 来源链接
                ② Worker【情报提炼】：要点 / 变化点 / 影响评估
              Leader 汇总（按报告模板 Skill）→ 公开信息简报
```

**数据边界**：只用来自搜索引擎可见的公开信息，并标注链接；不做站点爬取，不抓需登录或受限的数据；涉及招聘只收集公开发布的职位信息，不收集简历。报告是信息汇总与线索整理，不作为经营决策依据。不替代法务合规审查，不判断文案能不能对外发布。

---

## 二、可以问的角度

不必按部门各开一个助手。下面每个角度都是同一套「检索 → 摘要」；Leader 把对象和角度问清楚即可。

### 2.1 公司与产品动态

某家公司或某个产品最近公开渠道里做了什么。

| 角度 | 可以这样问 |
|---|---|
| 产品功能 | 贝壳找房近三个月租房产品有哪些公开的功能更新？做内部周报用。 |
| 营销动作 | 闲鱼最近在二手这块公开的营销打法是什么，有哪些主题活动？ |
| 业务布局 | 安居客近半年公开报道里，业务重点有没有从经纪转向其他方向？ |
| 组织人事 | 目标：某公司；维度：组织人事；范围：近一个月；用途：汇报。直接开始。 |

### 2.2 行业与舆论

不点名一家公司，看赛道或议题在公开渠道里怎么被写。

| 角度 | 可以这样问 |
|---|---|
| 行业新闻 | 近一个月分类信息 / 本地生活赛道，公开报道里在吵什么？ |
| 舆情点名 | 这周公开渠道里「虚假房源」「收费不透明」有没有点名 58、贝壳或闲鱼？给品质周会用。 |
| 议题跟踪 | 近一季度公开报道里，租房「指导价 / 核验」被提到的频率和口径有没有变？ |

### 2.3 公开招聘与人才

只看官网、招聘页、宣讲公开稿，不看简历。

| 角度 | 可以这样问 |
|---|---|
| 社招扩张 | BOSS 直聘近半年算法岗位在招什么方向，技能要求有什么变化？做招聘策略参考。 |
| 校招口径 | 今年字节、美团校招官网和宣讲口径是什么？ |
| 雇主品牌 | 某公司近一季度公开渠道里，校招/社招宣传主打什么卖点？ |

### 2.4 公开文件与披露

财报、公告、政策原文、召回说明——先定位页面，再抽能公开引用的写法。

| 角度 | 可以这样问 |
|---|---|
| 财报口径 | 贝壳最近一份季报里租赁和家服怎么披露的，公开口径是什么？ |
| 政策原文 | 上海这轮租赁指导价和核验新规，公开文件里怎么写的？近三个月，给产品内部参考。 |
| 召回与必显 | 某车型召回公告出来后，公开材料要求展示哪些说明？ |
| 套餐与定价 | 几个平台官网上的套餐价、用量阈值、超额计费怎么写的？列个对照。 |
| 厂商发布 | 某云厂商 / 开源项目最近两个版本的官方 Release 和博客里，写了哪些 breaking change？ |

### 2.5 研究观点与供应链公开信息

同样是公开网页，只是对象换成研报、供应商新闻、专利论文。

| 角度 | 可以这样问 |
|---|---|
| 公开研报 | 近一季度券商对某赛道的公开观点怎么变，有哪些带出处的结论？ |
| 供应商新闻 | 某关键供应商近期有没有停产、涨价、处罚的公开报道？ |
| 专利与论文 | 某技术方向近一年公开专利和顶会论文主题分布是什么？ |

### 2.6 不问这个助手的事

这些不是「检索 + 摘要」，不要塞进本花名册：

- 这段对外文案能不能发、有没有广告法 / 涉诉风险（合规审查）
- 隐私政策逐项对照、收集项抽取（另开合规类助手）
- 改简历、模拟面试、规划行程、家装报价、投保建议

## 三、产品形态与实现方式

### 3.1 用户看到的是什么

AgentScope 把**多用户 Agent 后端**做成 Agent Service，并在 `examples/web_ui` 里提供现成 Web 界面。用户路径只有三步：

1. 打开浏览器访问内网地址，第一次填服务地址和用户名
2. 左侧选择「公开信息简报助手」，点「新会话」
3. 用大白话提问

不需要调 HTTP、上传 API Key、创建智能体，也不需要知道 Team 或 MCP。

### 3.2 我们要做的事

| 工作项 | 内容 | 工作量 |
|---|---|---|
| 服务配置 | 写一个 `main.py`，**调用** `create_app`，传入本公司的存储、消息总线、工作区、搜索 MCP | 约 100 行 |
| 智能体配置 | 在 Web 界面里创建 1 个 Leader + 2 个专家，填名称、系统提示词、邀请说明 | 界面操作 |
| 报告模板 | 一个 `SKILL.md`，规定简报排版和免责口径 | 一个文件 |
| 部署 | uvicorn 起服务，前端静态构建后挂 nginx | 常规部署 |

不写 HTTP 路由、不写前端、不设计数据库表。对话、会话、流式返回、多用户隔离、状态持久化都是框架给的。

`create_app`（`_app.py`）已经装好 FastAPI 和全部路由，但必须由调用方传入 `storage`、`message_bus`、`workspace_manager`。`main.py` 就是这一层接线。

| | `_app.py` 的 `create_app` | 我们的 `main.py` |
|---|---|---|
| 角色 | 工厂：装配路由、会话、SSE、权限钩子 | 入口：选实现、读环境变量、启动 uvicorn |
| HTTP / 前端 / 表结构 | 已经有 | 不写 |
| 连哪套 PG、Redis | 不知道 | `AGENTSCOPE_PG_URL`、`AGENTSCOPE_REDIS_*` |
| 搜索 MCP、报告 Skill | 可选参数，默认没有 | `default_mcps`（Tavily）、`skill_paths` |
| 别人打开就能聊 | 默认各用户自己建智能体 | `AdminCatalogPolicy` 把运维账号下的助手只读共享出去 |

| | 官方 `agent_service/main.py` | 本次 `local_eval/main.py` | 为啥要换 |
|---|---|---|---|
| 存储 | `RedisStorage` | 公司 PostgreSQL | 多节点、会话落库 |
| 消息总线 | `InMemoryMessageBus` | `RedisMessageBus` | 多实例互相唤醒、续聊 |
| 默认 MCP | Playwright + 可选高德 | Tavily 搜索 | 要搜公开网页；Invite 出的专家吃不到会话级 MCP，必须种在工作区默认里 |
| 谁看得到助手 | 每人自己建 | 只读共享运维账号下的 Leader/专家 | 打开就能聊 |
| 报告 Skill | 无 | `intel-report` | 每个用户工作区同一份简报模板 |
| 知识库 / 飞书 / 长期记忆 | 示例里开了 | 不开 | 本次不用 |

### 3.3 部署形态

| 项 | 选择 | 说明 |
|---|---|---|
| 服务 | `create_app` + uvicorn | 一个进程即一个服务实例 |
| 前端 | 框架自带 Web UI | `pnpm build` 后由 uvicorn 同进程托管 |
| 状态存储 | PostgreSQL | 智能体 / 会话 / 消息 / 会话短期状态 |
| 运行时协同 | Redis MessageBus | 会话锁、唤醒、流式消息扇出 |
| 执行环境 | LocalWorkspaceManager | 每个智能体一个工作目录 |
| 多节点 | 2 个实例共享同一套 PG + Redis | 同一会话可在任意实例续聊 |

### 3.4 三项硬性要求

| 要求 | 落实方式 |
|---|---|
| HTTP 服务对外 | `create_app` 生成 FastAPI，对话走 HTTP，回复走 SSE |
| 短期记忆与上下文 | 同一会话内多轮澄清自动累积；接近窗口上限时框架压缩历史 |
| 多节点部署 | 状态在 PostgreSQL，实例之间通过 Redis 协同 |

## 四、AgentScope 能力与使用方式

### 4.1 四层用法

| 层 | 解决什么 | 在本助手中怎么用 |
|---|---|---|
| Agent 层 | 单个智能体如何思考和回答 | Leader 多轮澄清；专家单轮产出 |
| 工具层 | 能力如何扩展 | MCP 做搜索；Skill 做简报模板 |
| 多智能体层 | 如何协作 | 花名册常驻，Leader 运行时邀请检索再请提炼 |
| 服务层 | 如何对外、如何扩容 | HTTP + SSE；PG + Redis |

### 4.2 能力—概念—用法映射

| AgentScope 能力 | 涉及概念 | 在本助手中的用法 |
|---|---|---|
| 模型接入 | Credential | 运维预置一份 ChatLing 凭证，用户无感 |
| 对话内核 | Message / Event、ReAct | Leader 问清对象、角度、时间范围、用途 |
| 记忆与上下文 | Session、上下文压缩 | 同一会话累积澄清结果；长对话自动压缩 |
| 角色定义 | 系统提示词 | 检索只查、提炼只总结 |
| 工具扩展 | Skill | Leader 挂 `intel-report`，统一排版与免责口径 |
| 工具扩展 | MCP | 信息检索使用搜索 MCP |
| 执行环境 | Workspace | 每位专家独立工作目录 |
| 多智能体 | Team、AgentInvite、TeamSay | 专家可被邀请；Leader 运行时组队 |
| 服务化 | `create_app`、Chat、SSE | HTTP 对外，回复流式返回 |
| 分布式 | Storage + MessageBus | PG 存状态，Redis 做锁与扇出 |
| 多用户 | 资源访问策略 | 运维持有配置并只读共享；会话和工作区各归各人（见 5.1） |

**本次明确不做**：长期记忆、知识库 / RAG、定时任务、IM 渠道、容器与云沙箱工作区。

### 4.3 部门分享

讲稿与讲法见 `intel_share.md`。主线：先演示本助手，再用 SDK 从零拼同一套后端（`sdk_briefing.py`），最后对照 `create_app`。

## 五、待确认项

### 5.1 用户接入方式（需要拍板）

框架默认按用户隔离，新用户名进来是空列表。Leader + 两位专家从哪来：

| 方案 | 做法 | 用户体验 | 代价 |
|---|---|---|---|
| A. 用户自建 | 每人自己配凭证、建 3 个智能体、写提示词 | 差 | 不像产品 |
| **B. 运维持有 + 共享给全员** | 运维 admin 持有一份凭证和 3 个智能体，对所有人只读可见 | 打开即用 | 约 20 行策略类 |

**建议选 B。** 用 `ResourceAccessPolicyBase`：任何人只读访问运维账号下那几个资源。共享的是配置，不是对话。

| 对象 | 归属 |
|---|---|
| 智能体（提示词、编排） | 运维 admin，只读 |
| 模型凭证 | 运维 admin，只读（接口里掩码） |
| 会话与消息 | 各用户自己 |
| 工作区 | 按「用户 + 智能体」划分 |

搜索 MCP 和报告 Skill 不走共享策略，启动时种进所有工作区默认配置即可。

内部试用可让用户填工号；正式推广在服务前加 SSO，写入用户身份，智能体配置不用改。

### 5.2 部署环境

- 线上：申请 Redis；PostgreSQL 用现有库
- 本地：两个进程连同一套 Redis + PG，验证跨实例续聊

### 5.3 搜索服务

信息检索依赖外部搜索 API。当前免费额度足够演示与内部试用。以后换搜索服务只改一处配置，提示词和编排不用动。
