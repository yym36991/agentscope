# 58 竞品与行业情报助手 — 应用设计说明

基于 AgentScope 的多智能体应用。用户打开浏览器即可使用，不需要调接口、不需要写代码。

---

## 一、应用场景

各场景共用同一套架构：专家花名册常驻，Leader 多轮澄清后按需组队（可串行、可并行、可跳过）。
**本次只实现场景一**；场景二用来说明换数据源和专家即可复用，不改服务代码。
场景三至六是和前两个完全不相干的 C 端助手（保险对照、家装、假期出行、求职准备），只写清怎么用，本次不实现。

### 场景一：58 竞品与行业情报助手（本次实现）

面向市场、产品、运营、HR、法务等部门的情报助手。用户提出关注的竞品或行业方向，
Leader 多轮澄清后按需编排专家，产出一份带来源链接的情报分析报告。

**专家花名册**（常驻，可单独咨询，也可被 Leader 拉进团队）

1. **信息检索** — 挂载搜索引擎 MCP，获取公开实时新闻与动态，返回带链接的事实条目
2. **情报提炼** — 提炼关键变化点、业务动作、影响评估
3. **合规校验** — 涉诉表述、政策风险、绝对化用语等做合规过滤

**链路一：竞品与行业动态**（产品 / 运营；也可是公关、战略、房产、汽车）

关注维度在澄清时选定：功能 / 营销 / 业务是默认；舆情、财报、房产调控、汽车车源也走这一条，不是新助手。

```
产品/运营 ──HTTP──► Leader【情报助手】
                  （多轮澄清：目标竞品或行业、关注维度、时间范围）
                    ① Worker【信息检索】：公开新闻与动态 + 来源链接
                    ② 并行：
                       ├─ Worker【情报提炼】：变化点 / 业务布局 / 影响评估
                       └─ Worker【合规校验】（可选）：关注政策风险或涉诉动态时 Invite
                  Leader 汇总（按报告模板 Skill）→ 竞品动态报告
```

**链路二：人才情报**（HR / 招聘 / 校园招聘）

社招岗位变化是默认；校招与雇主品牌也走这一条。

```
HR/招聘负责人 ──HTTP──► Leader【情报助手】
                      （多轮澄清：目标公司、重点岗位与职级、时间范围）
                        ① Worker【信息检索】：公开招聘信息与人才动态
                        ② Worker【情报提炼】：岗位扩张方向 / 技能要求变化
                      Leader 汇总 → 人才情报简报
```

**链路三：合规直连**（法务 / 合规 / 运营）

政策风险、涉诉是默认；隐私政策对照也走这一条（需要时再请增补专家）。

```
法务/合规/运营 ──HTTP──► Leader【情报助手】
                        └─ Worker【合规校验】（与花名册同一位专家）
                      Leader 汇总后回复 → 政策风险评估与建议
```

三条链路共用同一批专家，区别只在 Leader 运行时决定叫谁、并行还是串行、要不要跳过某一步。

**数据边界**：来源限定为搜索引擎可见的公开信息并标注链接；不做站点爬取，不抓取需登录
或受限的数据；人才链路只使用公开发布的职位信息，不涉及个人简历。报告定性为信息汇总与
线索整理，不作为经营决策依据。不使用个人知识库账号代全员拉内部文档。

**各链路问法扩展举例**（多数仍用默认三人；Leader 在 Invite 时把任务说具体即可，不必为每个业务线新开专家）

| 链路 | 谁来问 | 问题示例 | 现有三人怎么覆盖 | 才值得另加的专家 |
|---|---|---|---|---|
| 链路一 竞品与行业 | 公关 / 品质 / 运营 | 这周公开渠道里「虚假房源」「收费不透明」有没有点名 58 或贝壳、闲鱼？给品质周会用。 | 信息检索找公开报道；情报提炼归纳谁被点名、议题是什么；合规校验过滤未证实指控 | 议题很多、要按周归档时，再加**议题聚类** |
| 链路一 竞品与行业 | 战略 / 市场 | 贝壳最近一份季报里租赁和家服怎么披露的，和我们能公开引用的口径差在哪？ | 信息检索定位公告页；情报提炼抽披露口径；合规校验标「可对外引用 / 仅内部参考」 | 要按科目逐年抽数时，再加**财务指标提炼** |
| 链路一 竞品与行业 | 房产产品 / 城市运营 | 上海这轮租赁指导价 / 核验新规，挂牌页和经纪人话术要不要加提示？ | 信息检索找政策原文；情报提炼评估对挂牌/话术的影响；合规校验看展示话术能不能这么写 | 不另加 |
| 链路一 竞品与行业 | 汽车事业群 | 某车型召回公告出来后，58 汽车详情页要不要展示召回说明，价格和配置字段怎么写？ | 同上：检索公告 → 提炼对详情页字段的影响 → 合规看必显项 | 不另加 |
| 链路二 人才 | HR / 校园招聘 | 今年字节、美团校招官网和宣讲口径是什么，我们宣讲 PPT 里薪资和「包分配」类表述要避哪些坑？ | 信息检索校招页/宣讲公开稿；情报提炼对照岗位与宣传口径；合规校验盯绝对化承诺 | 不另加 |
| 链路三 合规 | 法务 / 安全 / 产品 | 贝壳 App 和闲鱼公开隐私政策里，位置信息、第三方 SDK 怎么写的，和我们对外口径差在哪？ | 信息检索拉公开政策页；情报提炼抽取收集项；合规校验对照我方对外口径 | 条款很长、要逐项对照表时，再加**收集项抽取** |

本次演示只用主花名册三人。上表「另加」列是以后可选，加到同一花名册，不改服务、不新开助手入口。舆情检索、公告检索、政策检索、车讯检索都还是**信息检索**；影响评估、口径对照都还是**情报提炼**；话术/必显项/招聘文案都还是**合规校验**，不要再注册同名切片。

### 场景二：58 开源代码评审助手（备选，本次不实现）

同一套架构换一批专家和工具即可成立——**换场景只改智能体配置与 MCP，不改服务代码**。
面向技术开发 / 架构师 / 安全。用户提供真实的公开 GitHub 仓库、PR 或 Issue 链接，
Leader 多轮澄清考察重点后编排专家，产出代码 Review 或技术选型评估报告。

**专家花名册**

1. **代码检索** — 挂载 GitHub MCP，读取真实 Commit、PR Diff、README 与活跃度
2. **代码分析** — 逻辑缺陷、性能隐患、可维护性
3. **合规校验** — 开源协议风险与密钥泄漏排查

**链路一：PR / Diff 评审**

```
开发者/架构师 ──HTTP──► Leader【代码评审助手】
                      （多轮澄清：PR 链接与变更范围、重点方向（性能/安全/规范））
                        ① Worker【代码检索】：GitHub MCP → PR Diff 与 Commit
                        ② 并行：
                           ├─ Worker【代码分析】：潜在缺陷 + 性能与可维护性建议
                           └─ Worker【合规校验】：License 风险 + 密钥泄漏扫描
                      Leader 汇总（按评审模板 Skill）→ PR 评审报告
```

**链路二：开源组件选型**

```
技术开发 ──HTTP──► Leader【代码评审助手】
                  （多轮澄清：Repo 地址、对比维度、业务使用场景）
                    ① Worker【代码检索】：GitHub MCP → Star 趋势 / Commit 活跃度 / README
                    ② Worker【代码分析】：架构优劣 / 维护状态 / 接入成本
                  Leader 汇总 → 技术选型建议
```

**链路三：单专家直连**

```
安全/合规 ──HTTP──► Leader【代码评审助手】
                    └─ Worker【合规校验】（与代码花名册同一专家）
                  Leader 汇总后回复 → 开源协议风险清单
```

**数据边界**：仅公开仓库与公开漏洞/Release 信息；不使用个人 Token 拉取私有仓；
不把内部代码发到公网。报告定性为技术参考，不替代人工合入决策。

### 场景三：保险对照助手（备选，本次不实现）

面向投保人：在公开在售的医疗 / 意外等保险产品里搜索，筛出满足要求的产品，做保项对照和情况总结。
用户可以说出产品名，也可以只说需求（年龄、城市、必须覆盖的责任）；Leader 多轮澄清后按需编排专家，去搜官网条款页和监管问答。

**专家花名册**

1. **条款检索** — 搜保险公司官网产品页、条款、监管问答，返回带链接的公开信息
2. **保障对照** — 把免赔、保额、住院前后、等待期等抽成对照表，并做情况总结
3. **除外责任** — 不保什么、停售说明、销售话术红线（可跳过）

**链路一：点名对照**

用户已有两 / 三款候选，关心若干字段（如免赔、质子重离子、等待期）。

```
投保人 ──HTTP──► Leader【保险对照助手】
                （澄清：哪两/三款、关心哪些字段）
                  ① Worker【条款检索】：官网条款页 + 链接
                  ② 并行：
                     ├─ Worker【保障对照】：免赔 / 保额 / 等待期等对照表
                     └─ Worker【除外责任】（可选）：不保清单
                Leader 汇总 → 条款对照（信息整理，不构成投保建议）
```

**链路二：提需求找产品再对照**

用户还没有锁定产品，先按条件筛候选，再对照关心的字段。

```
投保人 ──HTTP──► Leader【保险对照助手】
                （澄清：年龄城市、预算粗区间、必须覆盖的责任）
                  ① Worker【条款检索】：公开在售、名称可核验的候选
                  ② Worker【保障对照】：按用户关心字段对照
                Leader 汇总 → 候选 + 对照表 +「建议向销售核实」清单
```

**数据边界**：只用不登录可打开的公开条款 / 说明书；不代销、不算保费、不推荐。
输出是条款摘录与差异，投保以保险公司正式文件和持牌人员为准。

### 场景四：家装方案助手（备选，本次不实现）

给正在装、改、配家具的人用。毛坯全装、二手房翻新、只动厨卫水电、租房能改什么、软装配色、家具能不能进门，都问这一个助手。
Leader 先问清城市、住房性质（新房/二手/出租）、面积几居、这次动硬装还是软装家具、预算量级，再按需拉专家。对话就能开始；户型图只在排墙、点位、家具靠墙时有用。

**专家花名册**

1. **规范与案例检索** — 查找公开强制条文、验收标准、地区差异（如地暖、防潮、阳台封装），以及同类户型的公开案例
2. **方案与预算** — 拆改造围、施工大致顺序、材料分档、软装搭配、家具公开尺寸，给出费用粗框和取舍
3. **验收注意** — 隐蔽工程和水电怎么验、常见偷工减料；家具则核进门尺寸、安装和环保标识（可跳过）

**能问的事（同一花名册，Leader 决定叫谁）**

| 类型 | 问题示例 | 通常叫谁 |
|---|---|---|
| 规范 | 这城水电改造有哪些强制项？燃气和承重能不能动？ | 检索 + 验收 |
| 新房全装 | 毛坯 90 平三居先做哪几步，硬装软装预算怎么切？ | 检索 + 方案 |
| 旧房改造 | 二手房只翻厨卫，拆改和防水要注意什么？ | 三人看情况 |
| 局部改造 | 客厅换地板、改背景墙，要不要动水电？ | 检索 + 方案 |
| 租房 | 租客能改灯和窗帘吗，哪些动了退租要还原？ | 检索 |
| 材料 | 强化地板和岩板怎么选，公开环保等级差在哪？ | 检索 + 方案 |
| 特殊房间 | 儿童房安全、老人房无障碍、小户型收纳怎么做？ | 检索 + 方案 |
| 软装 | 北欧风窗帘灯具怎么配，灯光回路硬装时要预留什么？ | 检索 + 方案 |
| 家具 | 三人沙发和餐桌公开尺寸多少，电梯和门口过不过去？ | 检索 + 方案 |
| 收尾 | 工人说完工了，水电和防水我该怎么验？ | 验收（可加检索） |

**链路一：先问清规矩，再谈方案**

```
业主 ──HTTP──► Leader【家装方案助手】
              （澄清：城市、新房/二手/出租、面积几居、动哪几块）
                ① Worker【规范与案例检索】：强制项 + 同类案例 + 链接
                ② Worker【验收注意】（要验收或防偷工时）
              Leader 汇总 → 能做 / 不能做 + 验收要点
```

**链路二：硬装怎么干（全装或局部）**

```
业主 ──HTTP──► Leader【家装方案助手】
              （有户型图则读；没有就按面积几居估算）
                ① Worker【规范与案例检索】：不能动的结构/燃气/物业红线
                ② Worker【方案与预算】：顺序、材料档、费用粗框
                ③ Worker【验收注意】（可选）
              Leader 汇总 → 施工注意 + 预算切分（不是报价单）
```

**链路三：软装和家具怎么配**

```
业主 ──HTTP──► Leader【家装方案助手】
              （澄清房间用途、风格、预算；核对进门尺寸时用户型图）
                ① Worker【规范与案例检索】：公开参数、搭配案例
                ② Worker【方案与预算】：候选与尺寸粗框
              Leader 汇总 → 选型对照（不代购、不出效果图）
```

**数据边界**：只引用公开规范、公开案例和公开商品参数。预算是行情区间。
不出施工图和效果图，不替装修公司报价或下单。承重、燃气、外墙以物业和持证施工现场为准。

### 场景五：假期出行规划助手（备选，本次不实现）

把「从出发到回来」相关的公开信息收拢成一份能执行的安排。周末近郊、黄金周跨城、出差前后的空档、看展看比赛、探亲顺路玩、人还在路上要改第二天，都走这里。
用户可以没有目的地，也可以带着一张自己排的表或已经出票的确认单。Leader 只补齐时间、人数构成、交通偏好和硬约束（预算、体力、必须办的事），再决定请谁。

**专家花名册**

1. **交通与目的地信息** — 班次与在售口径、景区/场馆开放与预约、节假日与限行公告，以及往年同期客流、拥堵、天气气候带等公开材料
2. **行程与方案** — 从零给去处和节奏，或把已有日程拆开对照：通勤是否吃掉白天、闭馆日是否撞上、多城怎么换
3. **约束与风险** — 退改签、签证与入境、极端天气与停航停运、外交/卫生提醒、无障碍或携带宠物等限制（可跳过）

**能问的事**

| 类型 | 问题示例 | 通常叫谁 |
|---|---|---|
| 选目的地 | 只有三天假、想凉快、不想到处排队，有哪些城合适？ | 信息 + 方案 |
| 近郊/城市漫步 | 这周末不出省，博物馆和公园怎么串、哪天闭馆 | 信息 + 方案 |
| 跨城假期 | 高铁去一地玩三天，每天怎么排才不用折返跑 | 信息 + 方案 |
| 主题出行 | 滑雪、看海、赏枫、追演唱会/赛事，交通和住宿怎么配 | 信息 + 方案 |
| 多人节奏 | 带老人少步行、带小孩要午休、同事团建要晚上聚餐 | 方案为主 |
| 公务空档 | 会开完多一天，能不能转场另一座城，票怎么接 | 信息 + 方案 |
| 方案对照 | 网上抄来的六日线路第几天过满，怎么砍 | 信息 + 方案 |
| 远期 vs 临近 | 旺季哪周更挤、现在买票会不会更贵；出发前夜还变不变 | 信息 + 风险 |
| 出境与入境 | 免签还是要签、转机会不会二次入境、电话卡和现金 | 信息 + 风险 |
| 在途变更 | 航班延误、景区突然闭园，第二天怎么改 | 三人看情况 |
| 特殊约束 | 轮椅通道、宠物托运、自驾限行、行李额 | 风险为主 |

三条链路不按人群切。打工人调休、带娃、出差、游客是 Leader 澄清时的约束（体力、必须办的会、预算），同一套专家。
分叉看的是**用户已经带到哪一步**：

| 链路 | 用户手头有什么 | 助手交出什么 |
|---|---|---|
| 一 | 只有时间窗和忌讳，还没有目的地 | 候选方向 |
| 二 | 已有目的地，或自己排过一版，或已有票/订单 | 按天日程，或对原稿的对照/改法 |
| 三 | 在一或二之上，多了过不去的硬约束（出境、停运、行动不便等） | 在原结果上补风险核对；不是第三类用户 |

**链路一：还没有目的地**

```
用户 ──HTTP──► Leader【假期出行规划助手】
              （时间窗、出发地、忌讳：人多/太累/太贵）
                ① Worker【交通与目的地信息】：可达、开放、往年客流
                ② Worker【行程与方案】：若干去处及适合的玩法颗粒度
              Leader 汇总 → 候选方向
```

**链路二：已有目的地或已有一版安排**

```
用户 ──HTTP──► Leader【假期出行规划助手】
              （已有目的地、草稿或票根/订单）
                ① Worker【交通与目的地信息】：班次、闭馆、预约
                ② Worker【行程与方案】：按天串点或对原稿提改法
              Leader 汇总 → 可执行日程或对照意见
```

**链路三：一、二的可选加强（需要时 Invite 第三人）**

```
用户 ──HTTP──► Leader【假期出行规划助手】
              （出境、恶劣天气季、已出票、行动不便等）
                ① 仍走链路一或二
                ② 加 Worker【约束与风险】：签证入境、退改、停运、限制条件
              Leader 汇总 → 行程 + 须在官方渠道核验的链接
```

**数据边界**：班次、闭馆、签证、入境以官方站点为准；客流和拥堵来自公开报道与往年假期材料，不是实时热力图或票务库存。
不代购票、不锁价、不担保能订上。旺季以购票和预约页的实时状态为准。

### 场景六：求职准备助手（备选，本次不实现）

帮正在找工作或换工作的人把公开信息和自己的经历对上。不一定一上来就有目标岗：可以先聊背景、想去的城市、接受的节奏（校招/社招、是否转行），再收敛到可投的岗位名称；已经拿到 JD 或面试邀请的，再改简历、准备怎么答。
完整简历不是门槛。几段项目口述或粘贴即可；页数多或要按全文改一版时再把文件放进工作区。

**专家花名册**

1. **公司与岗位检索** — 查官网与招聘页 JD、团队公开介绍、面经和薪酬带，也能按城市/职级/方向筛一批名称可核验的岗位
2. **简历优化** — 对照目标 JD 调整结构和量化表述，不增加没有发生过的事实
3. **面试专家** — 专职面试：轮次与形式、常问与追问、答题结构、现场/视频注意、薪资与离职原因怎么说、哪些话属于夸大或泄密（可跳过；没到面试不必请）

第三人叫面试专家说得通：检索负责「外面怎么写」，简历负责「书面怎么呈现」，面试负责「开口怎么过关」。表述分寸放在面试专家里，不必再拆第四人。

两条链路不按应届/社招/转行切人，那些是 Leader 澄清时的约束。分叉看手头有没有目标岗：

| 链路 | 用户手头有什么 | 助手交出什么 |
|---|---|---|
| 一 | 只有经历和偏好，岗位名称还没定 | 可投方向 + 需核对的招聘页 |
| 二 | 已有公司/岗位、JD，或已约面试 | 改写稿和/或面试准备（按需叫简历、面试专家） |

**能问的事**

| 类型 | 问题示例 | 通常叫谁 |
|---|---|---|
| 定方向 | 后端五年、想去杭州或深圳，有哪些岗头和我现在做的接近？ | 检索 |
| 定城市/职级 | 同岗位北上深招聘页要求差在哪，我该投资深还是高级？ | 检索 |
| 对照 JD | 这两个岗位哪个更贴我简历上的项目？ | 检索 + 简历 |
| 改简历 | 按这个 JD 把项目经历改一版，数字不要编 | 检索 + 简历 |
| 只问面试 | 这个岗一面二面常问什么，项目怎么讲不夸大 | 检索 + 面试专家 |
| 临场 | 视频面试、英语轮、现场白板要注意什么 | 面试专家 |
| 谈条件 | 公开薪酬带大概在哪，离职原因怎么说才不踩红线 | 检索 + 面试专家 |
| 校招/转行 | 宣讲口径和正式 JD 不一致时以哪个为准；转行缺口怎么交代 | 检索 + 面试专家 |

**链路一：岗位还没定**

```
用户 ──HTTP──► Leader【求职准备助手】
              （城市、职级、是否转行、几段真实经历）
                ① Worker【公司与岗位检索】：可核验的岗头 + 公开 JD/薪酬带
              Leader 汇总 → 候选方向（不是内推、不保证有坑）
```

**链路二：已有目标岗**

```
用户 ──HTTP──► Leader【求职准备助手】
              （公司 + 岗位；简历可选；已约面试则说明轮次）
                ① Worker【公司与岗位检索】：JD / 面经
                ② 并行（按需）：
                   ├─ Worker【简历优化】：结构调整，不新增事实
                   └─ Worker【面试专家】：提纲、追问、临场与表述红线
              Leader 汇总 → 改写稿和/或面试准备材料
```

**数据边界**：公司、JD、薪酬只引用公开页面。不编造经历、不泄露前雇主未公开信息、不代投、不担保录用。
输出是准备材料，谈薪与入职以对方正式书面为准。

## 二、产品形态与实现方式

### 2.1 用户看到的是什么

AgentScope 不只提供后端。它把**多用户 Agent 后端**做成了一套现成能力，称为
**Agent Service**；同时在 `examples/web_ui` 里提供了一个**现成的 Web 界面**。
两者都不需要我们从零写。

用户的完整使用路径只有三步：

1. 打开浏览器访问内网地址，第一次填一下服务地址和用户名（相当于登录）
2. 在左侧选择「竞品与行业情报助手」，点「新会话」
3. 直接用大白话提问，剩下的交给它

用户不需要：调 HTTP 接口、上传模型 API Key、创建智能体、了解什么是 Team 或 MCP。
这些全部由我们提前配置好。

### 2.2 我们要做的事

| 工作项 | 内容 | 工作量 |
|---|---|---|
| 服务配置 | 写一个 `main.py`，**调用** `create_app`，传入本公司的存储、消息总线、工作区、搜索 MCP | 约 100 行 |
| 智能体配置 | 在 Web 界面里创建 1 个 Leader + 3 个专家，填名称、系统提示词、邀请说明 | 界面操作 |
| 报告模板 | 一个 `SKILL.md` 文件，规定报告排版和免责口径 | 一个文件 |
| 部署 | uvicorn 起服务，前端静态构建后挂 nginx | 常规部署 |

**不需要做的事**：不写任何 HTTP 路由，不写前端页面，不设计数据库表。
对话、会话管理、流式返回、多用户隔离、状态持久化都是框架给的。

`create_app`（`_app.py`）已经把 FastAPI 应用和全部路由装好了，**不能单独当成可运行的服务**。它要求调用方传入 `storage`、`message_bus`、`workspace_manager`，这些在框架里只有抽象基类和若干实现，没有「默认连上 58 的 PG / Redis / Tavily」。`main.py` 就是这一层接线，和官方 `examples/agent_service/main.py` 是同一用法。

| | `_app.py` 的 `create_app` | 我们的 `main.py` |
|---|---|---|
| 角色 | 工厂：装配路由、会话、SSE、权限钩子 | 入口：选实现、读环境变量、启动 uvicorn |
| HTTP / 前端 / 表结构 | 已经有 | 不写 |
| 连哪套 PG、Redis | 不知道 | `AGENTSCOPE_PG_URL`、`AGENTSCOPE_REDIS_*` |
| 搜索 MCP、报告 Skill | 可选参数，默认没有 | `default_mcps`（Tavily）、`skill_paths` |
| 别人打开就能聊 | 默认各用户自己建智能体 | `AdminCatalogPolicy` 把运维账号下的助手只读共享出去 |

不写 `main.py` 就没有进程可起，也没有地方声明「用公司的库、用 Tavily、用共享花名册」。写了也不等于自研服务，路由仍全部来自 `create_app`。

也不能直接拿官方 `examples/agent_service/main.py` 当本次服务。那份是框架演示脚手架：存储用 Redis、总线用内存、还挂了知识库、飞书/Discord、长期记忆、浏览器 MCP。和本次硬性要求（公司 PG、多节点 Redis 总线、打开就能聊、检索用 Tavily）对不上。我们这份仍是同一句 `create_app(...)`，只换了传入的实现、去掉演示用能力。

| | 官方 `agent_service/main.py` | 本次 `local_eval/main.py` | 为啥要换 |
|---|---|---|---|
| 存储 | `RedisStorage`（本机 Redis） | 公司 PostgreSQL | 多节点、会话落库；不自建表，框架 `create_tables` |
| 消息总线 | `InMemoryMessageBus`（单进程） | `RedisMessageBus` | 两个实例才能互相唤醒、续聊 |
| 默认 MCP | Playwright 浏览器 + 可选高德 | Tavily 搜索 | 情报助手要搜公开网页；且 Invite 出的专家吃不到会话级 MCP，必须种在工作区默认里 |
| 谁看得到助手 | 每人自己建 | `AdminCatalogPolicy` 只读共享运维账号下的 Leader/专家 | C 端打开就能聊，用户不创建智能体 |
| 报告 Skill | 无（另接 ClawHub） | `skill_paths` 种入 `intel-report` | 每个用户的工作区都能套同一份报告模板 |
| 知识库 / 飞书 / 长期记忆 | 示例里开了 | 不开 | 本次不做内部知识库、不做 IM 适配、不引入额外记忆组件 |

### 2.3 部署形态

| 项 | 选择 | 说明 |
|---|---|---|
| 服务 | `create_app` + uvicorn | 一个进程即一个服务实例 |
| 前端 | 框架自带 Web UI | 构建成静态文件，浏览器直连服务 |
| 状态存储 | PostgreSQL | 智能体 / 会话 / 消息 / 会话短期状态 |
| 运行时协同 | Redis MessageBus | 会话锁、唤醒、流式消息扇出 |
| 执行环境 | LocalWorkspaceManager | 每个智能体一个工作目录，放技能和工具配置 |
| 多节点 | 2 个实例共享同一套 PG + Redis | 同一会话可落在任意实例上续聊 |

我们在 `create_app` 这一层需要做的选型决策只有四个：存储与总线用什么、
工作区用哪种执行环境（本次选本地目录，最简单）、模型凭证由运维统一持有还是用户自带
（本次选运维持有）、权限模式是否开启人工确认（本次选宽松，不打断对话）。

### 2.4 三项硬性要求的落实

| 要求 | 落实方式 |
|---|---|
| HTTP 服务对外 | `create_app` 直接生成 FastAPI 应用，对话走 HTTP，回复走 SSE 流式推送 |
| 短期记忆与上下文管理 | 同一会话内多轮澄清自动累积上下文；接近模型窗口上限时框架自动压缩历史并保留任务要点，无需我们干预 |
| 多节点部署 | 状态全在 PostgreSQL，实例之间通过 Redis 协同；起两个进程即两个节点，同一会话在任意节点都能继续 |

## 三、AgentScope 能力与使用方式

### 3.1 四层用法

| 层 | 解决什么 | 在本应用中怎么用 |
|---|---|---|
| Agent 层 | 单个智能体如何思考和回答 | Leader 多轮澄清需求；专家单轮产出结果 |
| 工具层 | 智能体的能力如何扩展 | MCP 提供搜索检索；Skill 提供报告模板 |
| 多智能体层 | 多个智能体如何协作 | 专家花名册 + Leader 运行时按需组队、可并行 |
| 服务层 | 如何对外服务、如何扩容 | HTTP + SSE 对外；PG + Redis 支撑多实例 |

### 3.2 能力—概念—用法映射

| AgentScope 能力 | 涉及概念 | 在情报助手中的用法 |
|---|---|---|
| 模型接入 | Credential | 运维预置一份 ChatLing 凭证（OpenAI 兼容），用户无感 |
| 对话内核 | Message / Event、ReAct 循环 | Leader 边想边问，逐步澄清目标竞品、关注维度、时间范围 |
| 记忆与上下文 | Session 短期状态、上下文压缩 | 同一会话内累积多轮澄清结果；长对话自动压缩保留任务要点 |
| 角色定义 | 系统提示词 | 花名册中每位专家的职责边界与输出格式 |
| 工具 | Tool / Toolkit、内置工具 | 智能体自带文件读写、检索等工作区工具；读取 Skill 模板即用其中的读取工具 |
| 工具扩展 | Skill | Leader 挂 `intel-report` 报告模板，统一排版与免责口径 |
| 工具扩展 | MCP | 信息检索专家使用搜索 MCP 获取公开实时信息 |
| 执行环境 | Workspace | 每位专家有独立工作目录，技能与工具互不干扰 |
| 多智能体 | Team、AgentInvite、TeamSay | 专家开启「可被邀请」并写用途说明，Leader 运行时邀请，可并行派活 |
| 服务化 | `create_app`、Chat、SSE | HTTP 对外提供服务，回复流式返回 |
| 分布式 | Storage + MessageBus | PG 存状态，Redis 做会话锁与消息扇出，同一会话跨实例续聊 |
| 多用户 | 资源访问策略 | 运维 admin 账号持有凭证与智能体，全员只读共享；会话与工作区各归各人（见 4.1） |

**本次明确不做**：长期记忆、知识库 / RAG、定时任务、IM 渠道接入、
容器与云沙箱工作区。这些是框架具备但本场景用不上的能力，分享时只说明适用边界，不落地实现。

### 3.3 部门分享大纲

1. 基础概念：Agent / Session / Workspace / Credential 分别是什么
2. 最小可用路径：从一份配置到能对话，中间发生了什么
3. 多轮记忆与上下文管理：会话状态与自动压缩
4. 工具扩展：MCP 与 Skill 的区别、各自适合什么
5. 多智能体：邀请机制、并行编排、与固定工作流的差异
6. 多用户：数据按用户隔离的边界在哪，运维预置的智能体怎么让所有人都能用
7. 多节点部署：状态放哪、实例之间怎么协同
8. 能力覆盖地图：用了什么、没用什么、什么时候该用

## 四、待确认项

### 4.1 用户接入方式（需要拍板）

框架的数据默认按用户隔离，**一个新用户名进来看到的是空列表**。
所以问题只有一个：那 4 个专家智能体从哪来。

两种做法：

| 方案 | 做法 | 用户体验 | 代价 |
|---|---|---|---|
| A. 用户自建（框架默认用法） | 每人自己配模型凭证、自己建 4 个智能体、自己写提示词 | 差，等于让用户自己配环境和智能体 | 与"面向用户的产品"不符 |
| **B. 运维持有 + 共享给全员** | 运维用 admin 账号持有唯一一份凭证和 4 个智能体，对所有人只读可见 | 打开即用 | 一个约 20 行的策略类 |

**建议选 B。**

A 是框架开箱的默认形态，适合开发者自用；但我们要交付的是产品，
不能要求业务同事先搞懂什么是智能体、什么是凭证，才能问出第一个问题。

B 用的是框架的**资源访问策略**（`ResourceAccessPolicyBase`）。它只有一个方法：
给定一个用户，返回"这个用户可以访问哪些别人的资源"。默认实现返回空列表，
所以现在新用户进来才是空的。我们把它换成"任何人都能只读访问运维 admin 账号那几个资源"即可。

关键在于**共享的只是配置，不是数据**，所以用户之间依然是隔离的：

| 对象 | 归属 | 说明 |
|---|---|---|
| 智能体（提示词、编排配置） | 运维 admin 账号，只读 | 全局唯一一份，改一次全员生效 |
| 模型凭证 | 运维 admin 账号，只读 | 接口返回时是掩码的，只有运行时能解开，用户看不到 Key |
| 会话与消息 | **各用户自己** | 会话按访问者的用户名存取，互相看不到 |
| 工作区（文件、运行痕迹） | **各用户自己** | 工作区按"用户+智能体"划分，天然隔离 |

前端不需要改任何代码：智能体列表会自动分成「我的」和「共享给我」两组，
共享的条目带「只读」标记，编辑和删除按钮自动禁用——这套交互框架已经内置了。

我们要做的只有三件事：

1. 用运维 admin 账号把凭证和 4 个智能体建好（就是现在界面上做的事，做一次）
2. 写一个策略类，对任何来访者返回这几个资源的只读引用（约 20 行）
3. `create_app` 时把策略传进去

搜索工具和报告模板不走上面的共享策略，而是在服务启动时声明为"所有工作区的默认配置"，
每个用户的工作区首次创建时自动带上——这是框架已有的参数，改一行即可，
搜索工具当前已经是这么接的。

**关于"不搞复杂方案"**：这 20 行不是锦上添花。
只要要求"用户打开就能用，且彼此看不到对话"，就必须有它，否则只能退回 A 让用户自建。
它也是框架给的标准扩展点，不是我们自己造的机制。

**关于用户身份**：框架通过请求头识别用户，本身不做登录鉴权。
内部试用阶段可以让用户自己填工号，隔离属于"防误看不防冒充"；
若要正式推广，在服务前面加一层内部 SSO，由它写入用户身份即可，
智能体配置和编排逻辑都不受影响。

### 4.2 部署环境

- 线上：需要申请一个 Redis 实例；PostgreSQL 使用现有数据库
- 本地验证：起两个进程连同一套本地 Redis + PG，验证同一会话跨实例续聊

### 4.3 搜索服务

信息检索专家依赖一个外部搜索 API。当前使用免费额度（每月 1000 次，
足够演示与内部试用）。若后续需要更好的中文检索效果或更大调用量，
更换搜索服务只需改一处配置，智能体的提示词与编排逻辑均不受影响。
